# Life Dashboard

A personal life dashboard built with Next.js, Tailwind CSS, and Supabase — tasks, habits, upcoming events, a daily journal, and weight training logs, all in one place.

## Getting Started

Install dependencies and run the development server:

```bash
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000) to see the dashboard.

## Tests

```bash
npm test
```

Runs [Vitest](https://vitest.dev) against every `src/**/*.test.ts` file — pure-logic unit tests only, no browser or database involved, so they run in under a second and need no Supabase credentials. This app went a long time without any automated tests at all — every feature in this codebase was instead verified once, by hand, in a temporary dev-preview page that got deleted afterward (see the "Verified..." paragraph closing most sections below), which meant zero regression protection: a later change to, say, `date-utils.ts` could silently re-break something already fixed once. The suite covers the trickiest, most bug-prone pure logic in the app — the exact modules that had a real, subtle bug caught and fixed at some point this session:

- `date-utils.test.ts`, `habit-utils.test.ts` (the lenient streak-forgiveness window and chain calendar), `daily-glance-utils.test.ts`, `dashboard-sections.test.ts` (`resolveSectionOrder`'s stale-id handling — the exact mechanism that safely retired Monarch), `cleaning-utils.test.ts` (the fixed weekly/biweekly/monthly scheduling logic — the most complex date math in the app), `contacts-utils.test.ts`, `meal-plan-utils.test.ts`, `workout-utils.test.ts` (exercise-name merge/normalization and estimated-1RM), and `restore-utils.test.ts`.

Every test constructs any "instant that matters as a local calendar day" (e.g. a habit's `created_at`) from local `Date` components (`new Date(year, month, day, hour).toISOString()`) rather than a hardcoded `"...Z"` literal — a literal UTC string round-trips back to a *different* local calendar day depending on whatever timezone the test happens to run in, which for a codebase this deliberately timezone-careful would be exactly the wrong kind of flaky. Caught by noticing this sandbox happens to run in UTC (where the literal-string version would have passed anyway, silently) and fixing it to be deterministic regardless of the runner's timezone. Not connected to CI (there is no CI configured for this project) — running it locally before pushing is on you for now.

Also server-only — read inside the `parseWorkoutText` Server Action.

Daily push reminders (Settings → Notifications) need a VAPID key pair — no third-party account, generate your own:

```bash

```

```
NEXT_PUBLIC_VAPID_PUBLIC_KEY=<the generated public key>
VAPID_PRIVATE_KEY=<the generated private key>

RLS on `habits` is scoped to `auth.uid()` directly; `daily_habit_completions` has no `user_id` of its own, so its policies check ownership via a join back to `habits`, same pattern as `session_exercises` → `workout_sessions`. - `20260807000000_add_journal_entries_delete_policy.sql` — adds a delete policy to `journal_entries`, which previously only had select/insert policies, so entries can be removed from the Journal card.
- `20260808000000_restructure_meal_plan_for_slots.sql` — restructures `meal_plan_entries` from one upserted-forever row per day into one row per `(week_start_date, day_of_week, meal_slot)`, adding `meal_slot` (Breakfast/Lunch/Dinner), `mode` (Custom/Eating Out/Leftovers), and `leftover_day_of_week` / `leftover_meal_slot` (which slot a Leftovers entry repeats). Backfills existing rows into the Dinner slot of the then-current week, in Custom mode. The old `unique (user_id, day_of_week)` constraint is replaced with `unique (user_id, week_start_date, day_of_week, meal_slot)`, since a day can now have three independent slots across many distinct weeks.
- `20260809000000_create_cleaning_tasks.sql` — creates `cleaning_tasks` (`name`, `frequency` constrained to `weekly`/`biweekly`/`monthly`) and `cleaning_task_completions` (`task_id`, `completed_at` — an append-only log, not a mutable "last done" flag) backing the Routine Cleaning Reminders card. RLS on `cleaning_tasks` is scoped to `auth.uid()` directly; `cleaning_task_completions` has no `user_id` of its own, so its policies check ownership via a join back to `cleaning_tasks`, same pattern as `daily_habit_completions` → `habits`.
- `20260810000000_create_weight_tracker.sql` — creates `weight_goal` (one row per user: `goal_weight`, `target_date`, upserted in place) and `weight_entries` (`entry_date`, `weight`, unique per user+date — logging again for a date overwrites it rather than adding a second entry) backing the Health card's Weight Tracker section. RLS is scoped to `auth.uid()` on both.
- `20260811000000_create_annual_goals.sql` — creates `annual_goals` (`title`, `description`, `position`), `goal_checkpoints` (one row per goal per quarter — `quarter` constrained to `Q1`-`Q4`, `target_description`, `completed`, `completed_at`, unique per goal+quarter), and `goal_checkin_notes` (`note`, `created_at` — an append-only log) backing the Annual Goals card. RLS on `annual_goals` is scoped to `auth.uid()` directly; the two child tables have no `user_id` of their own, so their policies (including delete, needed from the start for `on delete cascade` to work — see the note on `session_exercises` above) check ownership via a join back to `annual_goals`.
- `20260812000000_create_contacts.sql` — creates `contacts` (`name`, `category` constrained to `Family`/`Friends`/`Work`/`Extended Family`, `birthday`, `important_date` + `important_date_label`, `notes`, `gift_ideas`, `cadence_days`) and `contact_log` (`contact_id`, `contacted_at` — an append-only log, same shape as `cleaning_task_completions`) backing the Contacts / Relationship Tracker card. RLS on `contacts` is scoped to `auth.uid()` directly; `contact_log` has no `user_id` of its own, so its policies (including delete, from the start) check ownership via a join back to `contacts`.

### Timezones

Server Components and Server Actions run on the server (UTC on Vercel), not in the browser — any date/time logic that doesn't explicitly account for this ends up using the server's timezone instead of the signed-in user's, which showed up as the header clock and Upcoming Events running hours ahead of local time. Two distinct fixes are used throughout, depending on what's being computed:

1. **Formatting an absolute timestamp for display** (the header's date, event times, the Health card's "As of" line and recovery trend labels): moved into small Client Components so `toLocaleDateString`/`toLocaleTimeString` run in the browser, using its real timezone. Since Next still server-renders Client Components for the initial HTML, naively formatting on first render would still use the server's clock and then visibly (or, worse, silently) mismatch what the browser renders on hydration. Each of these is gated behind `useHasMounted()` (`src/lib/use-has-mounted.ts`, a `useSyncExternalStore`-based "is this the client yet" check) so they render a blank placeholder for the one frame before hydration completes, then the correct local value — avoiding React hydration-mismatch errors entirely rather than letting them happen and self-correct.
2. **Deciding what "today" is for a value being saved** (a new journal entry's `entry_date`, a new workout session's `session_date`): the server can't know the user's local date, so the client computes it (`getLocalDateString()` in `src/lib/date-utils.ts`, which reads local year/month/day — never `.toISOString()`, which gives the UTC date) and sends it explicitly. `JournalCard` sets a hidden field right at submit time; `WorkoutCard`'s save handler includes it directly in the payload. Both Server Actions fall back to computing the date themselves only if the field is missing or malformed.

Also fixed along the way: `new Date("yyyy-mm-dd")` parses bare date strings as UTC midnight, which rolls back a day in negative-offset timezones — `google-calendar-utils.ts`'s `parseEventDate()` constructs an explicit local date for all-day calendar events instead of handing the raw string to `Date` directly. `TasksCardBody.tsx` (Work Tasks) already did this correctly for Todoist due dates and needed no changes; Personal Tasks has no date-dependent display at all.

### Journal

- `src/lib/journal.ts` — `getJournalEntries()` fetches entries newest-first for Server Components.
- `src/app/actions/journal.ts` — `addJournalEntry` is a Server Action that inserts a new entry and revalidates the dashboard. `entry_date` comes from a hidden form field the client sets right at submit time (see [Timezones](#timezones)) rather than being computed on the server. `deleteJournalEntry` deletes an entry by id, scoped to the signed-in user (`user_id` check, backed by the delete RLS policy).
- `src/app/actions/transcribe.ts` — `transcribeAudio` is a Server Action that sends an uploaded audio file to OpenAI's Whisper API and returns the transcribed text. Runs entirely server-side so `OPENAI_API_KEY` stays private.
- `src/components/dashboard/JournalCard.tsx` — the textarea, the upload-and-transcribe control, and the entry list UI. Past entries are collapsed behind an "Entries (N)" toggle by default (same collapse pattern as Weight Training's Session History), expanding into a scrollable list capped at `max-h-80`. Each entry has a "Delete" button gated behind `window.confirm(...)`; deletion is optimistic (removed from the list immediately, reconciled with the server via `router.refresh()`), with the entry reappearing if the delete fails.
- The file picker and "Upload & Transcribe" button sit on the same condensed row as "Save Entry" (below the textarea) rather than in their own full-width row above it — file upload and text entry are actually two independent `<form>`s with two different Server Actions (`transcribeAudio` vs. `addJournalEntry`), and HTML forms can't nest, so "Save Entry" is rendered as a sibling of the audio form and tied back to the entry form via its `form="journal-entry-form"` attribute instead of living inside that form's own JSX subtree. Verified in a real browser that clicking it still submits the entry form correctly despite living outside it. Stacks into two rows below `sm:` breakpoints so the file input doesn't get crushed down to unreadable text on a phone-width screen.

To attach a voice memo: record it on your phone, upload the audio file via the "Upload & Transcribe" control, review/edit the transcribed text that appears in the textarea, then save as usual. Uploads are capped at 25MB (Whisper's own limit) via `serverActions.bodySizeLimit` in `next.config.ts`. Accepted formats: m4a (iPhone Voice Memos' default), mp3, mp4, wav, aac, webm, ogg, and flac — the file's extension is used to set the correct MIME type before it's sent to Whisper, since mobile browsers often report the wrong one.

### Weight Training

- `src/lib/workout-utils.ts` — pure, client-safe types and helpers (`getExerciseNames`, `getOneRepMaxSeries`, `estimateOneRepMax`, the `WORKOUT_CATEGORIES` constant) shared by the server data layer, `WorkoutCard`, and the chart component. Plus the exercise-consolidation helpers: `getExerciseUsage` (distinct stored names with session/set counts), `normalizeExerciseName` (a loose matching key), and `suggestExerciseMergeGroups`.
- `src/lib/workouts.ts` — `getWorkoutSessions()` fetches sessions (including `category`) with their nested exercises and sets, newest-first, for Server Components.
- `src/app/actions/workout.ts` — `parseWorkoutText` sends a freeform description to Claude (`claude-opus-5`, structured output via a Zod schema) and returns extracted exercises/sets; `saveWorkoutSession` requires a category (rejecting `null` with a clear error), validates it against `WORKOUT_CATEGORIES`, and inserts the (possibly edited) result into the three tables (`session_date` is sent by the client, see [Timezones](#timezones)); `deleteWorkoutSession` deletes a session, which cascades to its exercises/sets via foreign keys.
- `src/components/dashboard/WorkoutCard.tsx` — the "Quick log" textarea + Parse button, a required category selector (Chest/Back/Shoulder/Leg) alongside the session name field — attempting to save without picking one shows an inline error instead of submitting — an editable exercise/set builder (also usable directly for manual entry — just click "+ Add Exercise" without parsing anything), and the session history list. History is collapsed by default behind a "▸ Session History (N)" toggle; expanding it reveals the list capped at `max-h-96 overflow-y-auto`. Each session has a Delete button (optimistic removal, following the same local-state-synced-from-props pattern as Personal/Work Tasks).
- `src/components/dashboard/ProgressChart.tsx` — four category tabs; the exercise picker and chart below only ever show exercises from sessions in the selected category. Sessions without a category (including everything logged before this feature) don't appear under any tab. Plots an estimated one-rep max (Epley formula: `weight × (1 + reps / 30)`) rather than raw weight — for each session, the "best set" is whichever set produces the *highest estimated 1RM*, which isn't always the set with the most weight or the most reps.

The parsed result is never saved directly — it populates the same editable builder used for manual entry, so you can fix anything (including the category) before it's written to the database. Claude doesn't infer the category from the description; it's always your own selection.

#### Exercise picker and merging duplicates

`exercise_name` is free text, so the same lift typed slightly differently each time ("Bench Press" / "bench press" / "BB Bench Press") used to fragment into separate entries in the progress chart. Two changes address that — one preventing new drift, one cleaning up what's already there.

- `src/components/dashboard/ExerciseNamePicker.tsx` — the builder's exercise field is now a dropdown of every exercise already in your history, with a "+ New exercise…" option that swaps in a text input (and a "Choose existing" link back). The list is derived from history rather than a separate curated table, so a new exercise joins it automatically the moment it's saved — nothing to maintain. When there's no history yet, or when the quick-log parser returns a name that isn't in the list, it falls back to / preserves free text rather than dropping the value.
- `src/components/dashboard/ExerciseManager.tsx` — a "▸ Manage Exercises (N)" panel under Session History, listing every distinct stored name with how much history it carries (sessions · sets). Check two or more to merge them into one name, or use the **Possible duplicates** suggestions, which are pre-grouped by `normalizeExerciseName` — a key that flattens case, punctuation, extra whitespace, plurals, equipment shorthand (`bb`→barbell, `db`→dumbbell, `ohp`, `rdl`, …), and word order, so "Incline Bench Press" and "Bench Press Incline" match while "Bench Press" and "Incline Bench Press" correctly stay separate. The suggested target name defaults to whichever spelling has the most sets behind it, and is editable. Nothing is ever merged automatically.
- `src/app/actions/workout.ts` — `mergeExercises(names, canonicalName)` renames the matching rows. **Merging is a rename, not a delete**: every set stays attached to the session it was logged in, so the history is preserved intact and simply starts reporting under a single name. It matches on the exact stored string (which is why `getExerciseUsage` keys on the raw, untrimmed value — a row saved as `"Bench Press "` has to stay distinguishable from `"Bench Press"` or the update would silently skip it).

This needed a new migration: `session_exercises` had select/insert/delete policies but **no update policy**, so a rename would have silently affected zero rows under RLS. `20260816000000_add_session_exercises_update_policy.sql` adds it, scoped the same way as the others (joining back to `workout_sessions` and checking `user_id`).

The matching logic is pure and covered by `workout-utils.test.ts` (see [Tests](#tests)) — including a deliberate set of pairs that must *stay* distinct (Bench Press vs Incline Bench Press, Squat vs Front Squat, Deadlift vs Romanian Deadlift, Bicep vs Hammer Curl, Leg Press vs Leg Curl), since over-merging is the damaging failure here. The UI was then verified end-to-end in a headless browser against synthetic sessions containing known duplicates.

#### Personal record highlighting

Saving a workout now checks whether any exercise in it just beat its own all-time best, and celebrates it right there instead of leaving it to be noticed later by eyeballing the progress chart.

- `src/lib/workout-utils.ts` — `detectNewPersonalRecords(priorSessions, newSession)`: for each exercise in the session just logged, takes its best set by estimated 1RM (same "best set" definition `getOneRepMaxSeries` already uses for the chart) and compares it against the best 1RM across every prior session for that exact exercise (matched case-insensitively, same as the merge feature above). An exercise with no prior history at all is deliberately *not* flagged — there's nothing yet to have beaten, and treating every brand-new exercise as a "record" would cheapen the ones that actually are one. If the same exercise appears twice in one session (a rare manual-entry slip), only the single best set across both is compared, so one session never produces two separate "PR" results for the same lift.
- `src/components/dashboard/WorkoutCard.tsx` — `handleSave` computes new records against `localSessions` as it stood *before* the optimistic session is prepended (never against the array it's about to join), and shows them in a dismissible emerald banner under the Save button — "🎉 New personal record! Bench Press: 196 lb est. 1RM (up from 180 lb)" — following the same optimistic-then-revert convention as the rest of this form: the banner appears the instant the (optimistic) session is added, and clears if the save turns out to have failed, right alongside the rest of the optimistic state being rolled back.

Verified with a dedicated test suite (beats-prior-best, fails-to-beat, no-prior-history, best set within a multi-set session rather than the first one logged, comparing against the true historical max rather than just the most recent session, case-insensitive matching, multiple simultaneous PRs in one session, and the duplicate-exercise-in-one-session collapse), then end-to-end in a headless browser: logging a set that beats history shows the correct banner text and numbers immediately, and a non-PR save shows no banner at all.

### Work Tasks (Todoist)

- `src/lib/todoist.ts` — server-only: `getTodoistProjects()`, `getTodoistTasksForProjects()`, and `closeTodoistTask()` call the Todoist API directly with `TODOIST_API_TOKEN`; `getSelectedProjectIds()` reads the saved preference from Supabase. List responses are parsed defensively (a flat array or a `{results: [...]}` wrapper, whichever Todoist returns) since the exact response shape wasn't verifiable from this environment — worth confirming against a real account.
- `src/app/actions/todoist.ts` — `saveTodoistProjectSelection` upserts the chosen project IDs; `completeTodoistTask` closes a task in Todoist (via the API, not just locally) and revalidates the dashboard.
- `src/components/dashboard/TasksCard.tsx` (Server Component, fetches data) + `TasksCardBody.tsx` (Client Component, the interactive part) — a project picker (checkboxes, multi-select) shown until you've saved a selection, after that the task list with due dates and checkboxes. Checking a task off removes it immediately (optimistic) and calls Todoist to actually complete it; on failure the task reappears once fresh data loads. A "Change projects" link reopens the picker at any time.

Tasks shown are whatever's currently active (not completed) in the selected project(s). Three tabs split them by due date (compared by calendar date, not exact time): **Today** is due-today-or-overdue; **Tomorrow** is due exactly tomorrow; **Upcoming** is everything further out, including tasks with no due date at all. Within each tab, dated tasks sort soonest-first and undated tasks sort last. Due-date labels always show the full date (plus time, if the task has one) in every tab, including Today — unlike the Events card below, Today here can include overdue tasks, and dropping the date would hide how overdue they are. All three tabs cap the visible list height to roughly 5 tasks (`max-h-60`) with a scrollbar for the rest.

### Google Calendar

- `src/app/api/auth/google/route.ts` — starts the OAuth flow: redirects to Google's consent screen with `access_type=offline` + `prompt=consent` (so a refresh token is issued every time, not just on first consent) and a random `state` value stashed in a short-lived, `httpOnly` cookie for CSRF protection.
- `src/app/api/auth/callback/google/route.ts` — verifies `state`, exchanges the authorization code for tokens, and upserts them into `google_calendar_connections` for the signed-in user. Redirects back to the dashboard, adding a `?google_error=...` param on failure (surfaced as an inline message on the Events card).
- `src/lib/google-calendar.ts` — server-only: `isGoogleCalendarConnected()`, `getUpcomingEvents()` (refreshes the access token first if it's expired or about to expire, persisting the new one; fetches up to 20 events rather than just 5, so both grouped sections below have room to be populated), and `revokeGoogleToken()`.
- `src/lib/google-calendar-utils.ts` — pure, client-safe `CalendarEvent` type and helpers (`parseEventDate`, `isSameLocalDay`, `formatEventTime`, `formatEventDate`) shared by the server data layer and `EventsCardBody`.
- `src/app/actions/google-calendar.ts` — `disconnectGoogleCalendar` Server Action: revokes the token with Google and deletes the stored connection.
- `src/components/dashboard/EventsCard.tsx` (Server Component, fetches data + handles connect/disconnect/error states) + `EventsCardBody.tsx` (Client Component) — groups events into three tabs by the browser's local calendar day (see [Timezones](#timezones)): **Today** (time only, or "All day"), **Tomorrow**, and **Upcoming** (both show date + time, or just date for all-day events) — same layout pattern as the Work Tasks card. ### Health (Whoop)

- `src/app/api/auth/whoop/route.ts` — starts the OAuth flow: redirects to Whoop's consent screen requesting the `read:recovery read:cycles read:sleep offline` scopes (`offline` is what gets a refresh token issued) and a random `state` value stashed in a short-lived, `httpOnly` cookie for CSRF protection, following the same pattern as the Google Calendar connect route.
- `src/app/api/auth/callback/whoop/route.ts` — verifies `state`, exchanges the authorization code for tokens, and upserts them into `whoop_connections` for the signed-in user. Redirects back to the dashboard, adding a `?whoop_error=...` param on failure (surfaced as an inline message on the Health card).
- `src/lib/whoop-utils.ts` — pure, client-safe types (`HealthSnapshot`, `RecoveryPoint`) and helpers (`formatSleepDuration`, `recoveryColorClass`) shared by the server data layer and the chart component. `RecoveryPoint.timestamp` is a raw ISO instant rather than a pre-bucketed date string (see [Timezones](#timezones)).
- `src/lib/whoop.ts` — server-only: `isWhoopConnected()`, `getHealthSnapshot()` (latest recovery score, sleep summary, and strain, refreshing the access token first if it's expired or about to expire), and `getRecoveryTrend()` (recovery score for the last 7 days). `getValidAccessToken()` (private) is where the refresh actually happens — see the refresh-token note below, which documents a real bug that was fixed here.
- `src/app/actions/whoop.ts` — `disconnectWhoop` Server Action: deletes the stored connection. Unlike Google, Whoop's public API has no documented token-revocation endpoint, so there's nothing to call before deleting.
- `src/components/dashboard/HealthCard.tsx` (Server Component, fetches data + handles connect/disconnect/error states) + `HealthCardBody.tsx` (Client Component) — the "Connect Whoop" button when there's no connection, otherwise a compact recovery/sleep/strain snapshot plus the trend chart below it.
- `src/components/dashboard/RecoveryTrendChart.tsx` — a 7-day line chart of recovery score, styled the same way as the Weight Training progress chart (same SVG approach, hover tooltip, and date labels), with a fixed 0-100 y-axis since recovery is always a percentage.

Whoop's API response shapes (recovery/cycle/sleep record fields) are implemented from their public developer docs and parsed defensively (missing/unscored records are treated as "no data" rather than thrown), but weren't verifiable against a live account from this environment — worth double-checking field names against your own data once connected. Tokens are stored as plain columns protected by RLS, same caveat as the Google Calendar connection above.

**Refresh-token bug (fixed):** the connection used to silently die and demand a manual reconnect multiple times a day. Root cause — Whoop rotates the refresh token on every use: each `grant_type=refresh_token` call invalidates the refresh token that was just spent and returns a new one alongside the new access token. `getValidAccessToken()`'s update after a successful refresh only wrote the new `access_token`, discarding the new `refresh_token` Whoop had just issued. The very first automatic refresh worked fine, but it left the database holding a refresh token Whoop had already invalidated — so the *next* time the access token expired, the refresh call failed with `invalid_grant`, and it kept failing forever after, since nothing ever updated the stale token. The fix persists `refresh_token` (falling back to the existing one only if Whoop's response happens to omit it) on every successful refresh, alongside two related hardening changes: refresh failures now log Whoop's actual error body (e.g. `invalid_grant: The refresh token is invalid or has expired`) instead of just an HTTP status code, and a definitive 400 rejection deletes the stale connection so the dashboard correctly shows "Connect Whoop" again rather than a confusing "couldn't load data" message while still claiming to be connected — a transient 5xx/network failure is left alone rather than nuking a connection that's probably still fine.

**v1 API sunset (fixed, unrelated to the bug above):** the connection started dying again later, this time with a *different* Vercel log line — `Whoop API error on /recovery: 404` — coming from `whoopFetch()`, not from the refresh flow (no `invalid_grant`, no refresh-token error at all). Root cause: Whoop fully retired its `/developer/v1/*` data API in October 2025; `API_BASE` in `src/lib/whoop.ts` still pointed at `/developer/v1`, so every `/cycle`, `/recovery`, and `/activity/sleep` call started 404ing outright, independent of whether the access token was valid. Fixed by pointing `API_BASE` at `/developer/v2` instead — the resource paths, pagination params, and the response fields this app reads (`recovery_score`, `hrv_rmssd_milli`, `resting_heart_rate`, `strain`, `stage_summary`, `score_state`, etc.) are unchanged between v1 and v2, and the OAuth token endpoint (`/oauth/oauth2/token`) isn't versioned the same way and was never affected. Since this class of failure (valid token, but Whoop's data API itself rejecting the request) looked identical in the UI to a dead refresh token — both just showed "Couldn't load data from Whoop... try disconnecting and reconnecting," which is actively bad advice when the connection is fine — `getHealthSnapshot()` now returns a reason (`"auth_error"` vs `"api_error"`) alongside a null snapshot, and `HealthCard` shows a distinct, non-reconnect message for the latter.

#### Weight Tracker

A sub-section of the Health card, always shown regardless of whether Whoop is connected — it's the user's own logged data, not something Whoop provides.

- `src/lib/weight-utils.ts` — pure, client-safe types (`WeightEntry`, `WeightGoal`) and the derived-stat math:
  - `computeWeekOverWeekChange(entries, todayLocalDate)` averages this week's entries (Sunday through today) and last week's, returning `null` — rather than a misleading number — if either window has no logged entries at all.
  - `estimateWeeksToGoal(entries, goalWeight, todayLocalDate)` projects forward using the average rate of change since the first entry (total change ÷ weeks elapsed), applied to the remaining gap to the goal. Requires at least 2 entries *and* 14+ days of history — a wide gap between two entries would otherwise produce a wildly unreliable weekly rate — returning `{status: "insufficient_data"}` (surfaced as "Log a few more weeks to see an estimate") until then. Also handles a flat or wrong-direction trend (`{status: "no_progress"}`, e.g. weight went up while trying to lose) rather than showing a negative or infinite number, and a goal that's effectively already been reached (`{status: "already_at_goal"}`). The math itself generalizes to a goal above the current weight (gaining) as well as below it (losing), even though the rate is always framed as "closing the gap," not literally "rate of loss."
  - Both functions depend on the browser's local "today" (a week boundary is exactly the kind of thing that can land on the wrong side of the server/browser timezone gap — see [Timezones](#timezones)), so `WeightTrackerSection` computes them client-side, gated behind `useHasMounted()`, against data fetched server-side as plain props — same architecture as Habit Streaks' streak math, not the client-refetch approach Meal Plan needed (there's no "which week to query from the database" decision here — all entries are fetched once, and the week-bucketing is just local arithmetic over already-loaded data).
- `src/lib/weight.ts` — server-only `getWeightEntries()` (ascending by date) and `getWeightGoal()` (the single per-user row, or `null`).
- `src/app/actions/weight.ts` — `addWeightEntry` (upserts onto `(user_id, entry_date)` — logging again for a date overwrites it rather than creating a second entry), `deleteWeightEntry`, and `updateWeightGoal(goalWeight, targetDate)` (upserts onto `user_id`).
- `src/components/dashboard/WeightTrackerSection.tsx` — a goal form (weight + target date) and a log-weight form side by side, the week-over-week indicator (▲ red if gained, ▼ green if lost, "—" if unchanged, to 1 decimal place) and the time-to-goal estimate below that, the trend chart, then a collapsed-by-default history list (same `▸`/`▾` toggle pattern as Journal and Weight Training) with a Delete button per entry. The log-weight date field is an *uncontrolled* input (like Journal's date field) defaulting to today via a ref set in a mount effect, rather than React state — resetting controlled state inside the post-submit effect would trip the project's `react-hooks/set-state-in-effect` rule, while a plain DOM mutation on a ref doesn't.
- `src/components/dashboard/WeightTrendChart.tsx` — styled the same way as the Weight Training progress chart and the Whoop recovery chart (SVG line chart, hover tooltip, date labels), plus a dashed amber reference line at the goal weight. The value range used for the y-axis includes the goal weight (not just the logged data), with a little padding, so the reference line is never clipped against the plot's edge even if the goal is above or below every logged entry so far.

Checking the math against hand-worked cases (a losing trend, a gaining trend toward a higher goal, a flat trend, and a trend moving the wrong direction) confirmed the "no_progress" branch is reached instead of a nonsensical number whenever the trend doesn't support a projection.

### Habit Streaks

A fully custom habit tracker, replacing the original hardcoded placeholder — add/rename/delete habits, reorder them manually (up/down arrows, no drag-and-drop library), check them off per day, and see a running streak, best streak ever, and a 30-day chain calendar per habit.

- `src/lib/habit-utils.ts` — pure, client-safe types and the streak/calendar math:
  - `computeHabitStreaks(habit, todayLocalDate)` implements the lenient streak rule: **within any rolling 7-day window, one missed day is forgiven; a second missed day in that same window resets the streak to 0** (and the window itself resets, so the two miss-days that caused the break don't keep forcing resets for another week). A forgiven miss day doesn't interrupt the streak count — the counter keeps incrementing through it, the same way a "streak freeze" works in other habit trackers. A not-yet-completed "today" is never judged as a miss; it's simply excluded from the evaluated range until it's actually marked done or the day passes. `best` is the highest the streak counter ever reached, computed from the same scan. The evaluated range starts at the habit's `created_at`, converted to a **local** calendar date via `getLocalDateString(new Date(habit.created_at))` — an earlier version sliced the raw UTC-serialized timestamp directly, which could land on "tomorrow" relative to the user's local date for a habit created in the evening in a negative-offset timezone, making the range start after today and permanently stranding the streak at `0` no matter what got checked off.
  - `getChainCalendar(habit, todayLocalDate, days = 30)` returns the last 30 local calendar days (oldest first) with a `done` flag each, for the dot grid. Days before the habit existed just show as not-done (no separate "N/A" state).
  - All date math is done as `"yyyy-mm-dd"` string arithmetic via a local `addDays` helper — never through `Date`'s UTC-based parsing — since streaks and the chain calendar both depend on the browser's local calendar day (see [Timezones](#timezones)).
- `src/lib/habits.ts` — server-only `getHabits()`: fetches habits ordered by `position` with their nested completions, for the Server Component.
- `src/app/actions/habits.ts` — `addHabit` (appends at the end, `position = max + 1`), `renameHabit`, `deleteHabit` (cascades to its completions), `reorderHabit(habitId, "up" | "down")` (swaps `position` with the immediate neighbor — no bulk reorder endpoint, since the UI only ever moves one habit one step at a time), `setHabitCompletion(habitId, date, completed)` (upserts or deletes a `daily_habit_completions` row).
- `src/components/dashboard/HabitsCard.tsx` (Server Component, fetches data) + `HabitsCardBody.tsx` (Client Component) — the add-habit form, and the habit list. Streaks and the chain calendar are computed client-side against the browser's local date (mount-gated via `useHasMounted()`, same pattern as the timezone fixes elsewhere) rather than server-side, for the same reason: a Server Component can't know the user's real local "today". Each row: reorder arrows, a checkbox for today, the name (click to rename inline), a `🔥current · best N` badge, a delete button, and a row of 30 small dots (filled = done) underneath. Capped at `max-h-96 overflow-y-auto`, roughly 5 habits visible before scrolling, in the order you've set.

Toggling, reordering, renaming, and deleting are all optimistic (the UI updates immediately, then reconciles with the server) following the same local-state-synced-from-props pattern used by Personal/Work Tasks and Weight Training's session delete.

I verified the streak algorithm against a set of hand-worked cases (a single break within one window, two misses spaced more than 7 days apart correctly *not* compounding, and the two-miss-in-one-window reset) before wiring it into the UI — all matched the intended behavior exactly.

### Annual Goals

Up to 5 yearly goals (title + short description), each with four fixed Q1-Q4 checkpoints defined when the goal is created and checked off as they're achieved, a progress bar over those four checkpoints, and a running log of check-in notes. Starts empty — no seeded example goals.

- `src/lib/goals-utils.ts` — pure, client-safe types (`AnnualGoal`, `GoalCheckpoint`, `GoalCheckinNote`) and `computeGoalProgress(goal)` (how many of the four checkpoints are complete). `MAX_ANNUAL_GOALS = 5` is enforced in the add action, not the database — a straightforward application-level business rule rather than something worth a SQL constraint.
- `src/lib/goals.ts` — server-only `getAnnualGoals()`: fetches goals with their nested checkpoints and check-in notes, always normalizing checkpoints to exactly 4 entries in `Q1..Q4` order regardless of what's actually in the database.
- `src/app/actions/goals.ts` — `addAnnualGoal` (form action: title, description, and one target-description field per quarter, inserting the goal plus its 4 checkpoint rows in one action), `updateAnnualGoal` (title, description, and all 4 checkpoint target descriptions — doesn't touch `completed` status, which is only ever changed via the checkbox), `deleteAnnualGoal` (cascades to checkpoints and notes), `setCheckpointComplete` (also stamps or clears `completed_at`), and `addGoalCheckinNote`.
- `src/components/dashboard/AnnualGoalsCard.tsx` (Server Component) + `AnnualGoalsCardBody.tsx` (Client Component, the add-goal form and the goal grid) + `GoalItem.tsx` (Client Component, one goal's view/edit modes, progress bar, checkpoint checkboxes, and check-in notes). `GoalItem` has its own view/edit toggle per goal — editing covers title, description, and all 4 checkpoint descriptions at once, with Save/Cancel; there's no per-field inline editing like Habit Streaks' rename, since a goal has too many editable fields at once for that to stay compact.
- Each goal card shows only its title, description, and progress bar by default — the quarterly checkpoints (their Q1-Q4 target descriptions and completion status) and Check-in Notes are hidden behind a single "Checkpoints & Notes" `▸`/`▾` toggle, collapsed on load, since a checkpoint's target description can contain sensitive detail like a dollar amount that shouldn't be on-screen just from having the card open. Check-in Notes keeps its own nested `▸`/`▾` toggle underneath (same collapsed-by-default pattern as Weight Tracker's History and Weight Training's Session History, newest-first, capped at `max-h-48 overflow-y-auto`) — so opening "Checkpoints & Notes" reveals the checkpoint checkboxes plus the notes toggle itself, not the note text directly. Note timestamps are formatted client-side (mount-gated) since they're absolute instants, not date-only strings (see [Timezones](#timezones)).

The add-goal form itself is collapsed behind a "+ Add Goal" button rather than always visible, given how much space title + description + 4 checkpoint fields takes up; closing it after a successful add is handled by the same "adjusting state when a prop changes" render-time pattern used everywhere else in this app rather than a `useEffect`, since `addAnnualGoal` returns `null` on success — identical to its initial state — so there's no other way to detect success that wouldn't mean calling `setState` synchronously inside an effect (which this project's lint config specifically disallows).

### Routine Cleaning Reminders

A simple recurring checklist — no streaks, no chain calendar, just "is this task due yet." Add cleaning tasks (Vacuum, Clean bathroom, Deep clean fridge, …), each with a frequency of Weekly, Biweekly, or Monthly; a task becomes checkable again once its interval has passed since it was last marked done.

- `src/lib/cleaning-utils.ts` — pure, client-safe types and the due-status math. `CLEANING_FREQUENCY_INTERVAL_DAYS` maps each frequency to a fixed day count (7/14/30) rather than a calendar-aware interval like "the same day next month" — simpler, and matches "just a simple recurring checklist." `computeCleaningStatus(task, lastCompletedAt, now)` compares elapsed *real time* since the last completion against that interval (`now.getTime() - new Date(lastCompletedAt).getTime() >= intervalDays * dayMs`) rather than comparing calendar-day strings — an instant diff is timezone-independent (a millisecond is the same duration everywhere), unlike the "is it a new local day yet" checks the rest of this app has had to be careful about (see [Timezones](#timezones)). That means due/not-due status is safe to compute on the server, with no client-side correction step needed, unlike Habit Streaks, Meal Plan, or the Health card. It also returns `nextDueAt` (`lastCompletedAt` plus the interval, as an ISO instant) for every completed task, used by the Recently Completed section below. `isCleaningTaskVisible(task, withinDays = 7)` is the visibility filter described below — overdue (any amount) or due within the window.
- `src/lib/cleaning.ts` — server-only `getCleaningTasks()`: fetches tasks with their nested completions, takes the most recent `completed_at` per task, and runs it through `computeCleaningStatus`. Returns the *full* list, unfiltered — visibility filtering happens in the UI layer (see below), not here.
- `src/app/actions/cleaning.ts` — `addCleaningTask` (form action), `renameCleaningTask`, `updateCleaningTaskFrequency`, `deleteCleaningTask` (cascades to its completions), and `setCleaningTaskCompletion(taskId, completed)`. Marking a task done *inserts* a new row into `cleaning_task_completions` (an append-only log, not a mutable flag); unchecking it deletes only the most recent completion, as an undo for an accidental check.
- `src/components/dashboard/CleaningCard.tsx` (Server Component, fetches data) + `CleaningCardBody.tsx` (Client Component) — an add-task form (name + frequency), then the task list: a checkbox (checked = not due), the name (click to rename inline, same pattern as Habit Streaks), a frequency `<select>` that saves immediately on change, a delete button, and a status line ("Due now — done 9d ago" / "Not due yet — done 3d ago, due in 4d" / "Due now — never done"). Capped at `max-h-72 overflow-y-auto`.

Checking a task off is optimistic like everywhere else in this app, with one caveat: since the client doesn't track full completion history (only the derived due/not-due status), an optimistic uncheck approximates the result as "never done" rather than restoring the exact prior completion — `router.refresh()` immediately after reconciles it with whatever the server actually has on record.

Only tasks that are overdue (any amount) or due within the next 7 days are actually rendered — `CleaningCardBody` filters `localTasks` down to `visibleTasks` via `isCleaningTaskVisible` right before rendering the list, while every handler (toggle, rename, frequency change, delete) still operates on the full `localTasks` array. Hidden tasks aren't deleted or archived anywhere — they still exist and still get fetched on every load; they just don't pass the filter yet. Since visibility is recomputed fresh from `computeCleaningStatus` on every render (not stored as a flag), a task quietly reappears on its own once it drifts inside the 7-day window, with no separate "check for newly-due tasks" step needed. If every task is currently outside the window, the list shows "Nothing due or coming up in the next 7 days." instead of an empty list indistinguishable from having no tasks at all.

A collapsed-by-default "Recently completed" section sits below the main list — same `▸`/`▾` toggle pattern as Weight Tracker's History and Weight Training's Session History — showing exactly the complement of `visibleTasks` that's also been completed at least once (i.e. everything hidden by the filter above, minus tasks that have simply never been done, which show up as "Due now" in the main list instead). This only ever has entries for Biweekly or Monthly tasks in practice: a Weekly task's 7-day interval exactly matches the 7-day visibility window, so a freshly-checked Weekly task is already right at the edge of that window the moment it's checked and never actually leaves it. Expanding the section lists each task's name and its `nextDueAt`, formatted client-side (mount-gated, like every other absolute-timestamp display in this app — see [Timezones](#timezones)) since it's a real instant, not a date-only string. Sorted soonest-due-first, capped at `max-h-60 overflow-y-auto`.

### Contacts / Relationship Tracker

Sits right next to Routine Cleaning Reminders — same reminder-style shape, applied to people instead of chores. Add contacts with a name, category (Family/Friends/Work/Extended Family), optional birthday and "important date" (anniversary, work anniversary, etc., with a free-text label), notes, gift ideas, and a custom reach-out cadence in days (set per person, not a fixed set of options like Cleaning's Weekly/Biweekly/Monthly). A "Log Contact" button records today as the last-contacted date and resets the countdown.

- `src/lib/contacts-utils.ts` — pure, client-safe types and the due-status math, deliberately mirroring `cleaning-utils.ts`: `computeContactStatus(contact, lastContactedAt, now)` diffs elapsed real time against `cadenceDays * dayMs`, the same timezone-independent instant-diff approach as Cleaning Reminders (see [Timezones](#timezones)), and also returns `nextDueAt`. The one behavioral difference from Cleaning: `isContactVisible(contact)` has no 7-day lookahead window — a contact is either due or it isn't, since "coming up in the next week" doesn't map cleanly onto once-a-month or once-a-quarter cadences the way it does onto weekly chores.
- `src/lib/contacts.ts` — server-only `getContacts()`: fetches contacts with their nested `contact_log`, takes the latest `contacted_at` per contact, and runs it through `computeContactStatus`.
- `src/app/actions/contacts.ts` — `addContact` (form action), `updateContact`, `deleteContact` (cascades to its log), and `logContact` (defensively re-checks contact ownership before inserting into `contact_log`, since that table has no `user_id` of its own — same pattern as `setCleaningTaskCompletion`).
- `src/components/dashboard/ContactsCard.tsx` (Server Component) + `ContactsCardBody.tsx` (Client Component: category filter pills, the due list, the collapsed "Recently contacted" section, and the add-contact form) + `ContactItem.tsx` (Client Component, one contact's view/edit card).
- Due/overdue contacts render in the main list; everyone else who's been contacted at least once (never-contacted people show as due instead) sits behind a collapsed "Recently contacted, not due yet" section, same `▸`/`▾` pattern and sort-by-soonest-due as Cleaning's Recently Completed. A category filter ("All" plus each of the four categories) applies to both the main list and the collapsed section at once.

Building this surfaced a real bug before it ever shipped. The first pass gave `ContactItem` its own local optimistic copy of the contact — clicking "Log Contact" updated that local copy's `isDue` flag so the card's own text correctly flipped to "Not due yet," but `ContactsCardBody`'s due-list filter reads from its *own* `localContacts` array, which nothing had told about the change. The contact's card looked updated while it stayed stuck in the due list underneath it. A Playwright test targeting exactly this ("does logging a contact remove them from the main list") caught it: `ContactItem` was rewritten to be purely presentational — no data of its own, just `isEditing`/edit-form UI state — taking `contact`, a shared `isPending` flag, and `onLogContact`/`onUpdateContact`/`onDelete` callbacks that `ContactsCardBody` handles by updating its own `localContacts` and firing the real Server Action, exactly how `CleaningCardBody` already did it correctly from the start. Re-running the same test afterward confirmed the fix.

### Meal Planning & Grocery List

A wide card, directly below Habit Streaks: a weekly meal plan (Breakfast/Lunch/Dinner per day) on the left, an active grocery list plus a recurring "staples" list on the right.

- `src/lib/meal-plan-utils.ts` — the `DAYS_OF_WEEK` (Sunday first) and `MEAL_SLOTS` (`breakfast`/`lunch`/`dinner`) constants, the `MealMode` type (`"custom" | "eating_out" | "leftovers"`) and its display labels, and the client-safe `MealPlanEntry` type. `getWeekStartDate(localDateStr)` returns the Sunday starting the week containing a given local date; `getPreviousWeekStartDate` subtracts 7 days from that. All date math is `"yyyy-mm-dd"` string arithmetic via a local `addDays` helper, never through `Date`'s UTC-based parsing — the same pattern used throughout the app (see [Timezones](#timezones)), since a week boundary is exactly the kind of thing that can land on the wrong side of the server/browser timezone gap.
- `src/lib/meal-plan.ts` — server-only `getMealPlanForWeek(weekStartDate)`. Always returns exactly 21 entries (7 days × 3 slots), filling in `custom`/empty defaults for any slot that doesn't have a row yet for that particular week.
- `src/app/actions/meal-plan.ts` — `fetchMealPlanForWeek` (a plain callable, not a form action — see below), `updateMealPlanEntry` (upserts one slot onto `(user_id, week_start_date, day_of_week, meal_slot)`; clears `content` when the mode isn't Custom and clears the leftover reference when the mode isn't Leftovers, so stale data doesn't linger under an inactive mode), `copyPreviousWeek` (reads the previous week's entries, upserts every non-empty one into the current week, and returns the refreshed grid — a no-op error if last week was entirely empty), and `parseMealIngredients` (sends a meal's text to Claude, `claude-opus-5`, structured output via a Zod schema, returning a short list of likely grocery items).
- `src/components/dashboard/MealPlanSection.tsx` — renders immediately from a server-provided best guess at the current week (`initialWeekStartDate`/`initialEntries`, computed using the server's effectively-UTC clock — same "render a reasonable default, silently upgrade" pattern as `WeatherWidget`'s Charlotte fallback), then on mount compares that guess against the browser's real local week and, only if they differ, calls `fetchMealPlanForWeek` once to correct it — no loading flash in the common case, no network round-trip before the grid can render. Each of the 21 slots has a mode `<select>` (Custom/Eating Out/Leftovers) plus, depending on the mode: a text field (Custom, saved on blur) with a 🛒 button next to it, a plain "Eating Out" badge, or a second `<select>` listing every other slot in the week (Leftovers — e.g. "Monday Dinner"). "Copy previous week" duplicates last week's full plan (mode, content, and leftover references) into the current week as an editable starting point. The 🛒 button opens an inline ingredient-parsing preview below that slot: Claude's suggested ingredients appear as editable text rows (add/remove any of them) with "Add to Grocery List" and "Cancel"/"Close" buttons, so nothing is added to the grocery list without a chance to review it first.
- `src/lib/grocery-utils.ts` — client-safe `GroceryItem`/`GroceryStaple` types.
- `src/lib/grocery.ts` — server-only `getGroceryItems()` and `getGroceryStaples()`, both ordered oldest-first.
- `src/app/actions/grocery.ts` — `addGroceryItem` / `addGroceryStaple` (form actions), `toggleGroceryItem` (flips `checked`, doesn't delete), `clearCheckedGroceryItems` (bulk-deletes everything checked — the only way checked items are removed), `deleteGroceryStaple`, `addStapleToGroceryList` (a plain callable — not a form action — sharing the same insert as `addGroceryItem`, used by the staple quick-add chips), and `addItemsToGroceryList` (bulk insert, used by the meal plan's ingredient-parsing preview to add several items in one call).
- `src/components/dashboard/GroceryListSection.tsx` — staple chips at the top (tap the chip text to quick-add it to the list below; the small ✕ removes it from your staples, not from the active list, plus a compact inline "Add staple" field), then the manual add-item form, then the list itself. Checked items get a strikethrough and stay in place — they only disappear via the "Clear checked" button, which only appears once something is checked. Capped at `max-h-60 overflow-y-auto`. All mutations (toggle, quick-add, clear-checked, delete-staple) are optimistic, same local-state-synced-from-props pattern as Habit Streaks and Personal/Work Tasks.
- `src/components/dashboard/MealPlanGroceryCard.tsx` — the Server Component wrapper (`lg:col-span-3`, full-width) that fetches the server's best-guess current week's meal plan plus both grocery data sources in parallel, and lays out the two sections side by side.

The ingredient list Claude suggests is never added to the grocery list directly — it always lands in the editable preview first, mirroring how Weight Training's Claude-parsed workout populates an editable builder rather than saving straight to the database.

**Collapsible.** Being a wide, tall, two-section card, this is the one section with a "get it out of my way for now" collapse toggle (useful for anyone who doesn't need meal planning visible on every visit — e.g. while traveling) — `WidgetCard` gained an optional `collapsible` prop, only passed by `MealPlanGroceryCard`. The collapsed/expanded state is persisted in `localStorage` (keyed by the section's `id`, e.g. `dashboard-section-collapsed:meal-plan-section`), not Supabase — deliberately a lighter-weight, per-device preference rather than something synced across devices like drag-to-reorder's section order. `WidgetCard` reads it through `useSyncExternalStore` with a real (non-no-op) subscribe/notify, so the stored value can be read directly during render — no server/client hydration mismatch, and no extra render pass the way `useState` + `useEffect` would need — and any other collapsible card would immediately reflect a change made elsewhere. Collapsing just conditionally omits `children` from the render (children are still fetched server-side regardless, same as every other card) and swaps the plain `<h2>` title for a `▾`/`▸` toggle button, matching the existing checkpoint/notes disclosure-triangle convention used in Annual Goals. Verified with a temporary dev-preview page: toggling hides only that card's body (siblings untouched), `aria-expanded` tracks state, and the collapsed state survives a full page reload.

### Weather

A compact weather widget lives in the dashboard header, next to the date/email/Sign Out controls. No API key or database table required — it's a live fetch to [Open-Meteo](https://open-meteo.com) on every page load. Desktop always shows Charlotte, NC; mobile tries to upgrade to the device's actual location.

- `src/lib/weather-utils.ts` — pure, client-safe types (`WeatherSnapshot`, `HourlyForecast`) and a WMO weather-code → emoji/label lookup (`getWeatherIcon`, `getWeatherLabel`), plus `formatHour`.
- `src/lib/weather.ts` — `getWeatherSnapshot(latitude?, longitude?)` fetches current conditions, today's high/low, and the next 12 hours from Open-Meteo's `/v1/forecast` endpoint (`cache: "no-store"` so it's always fresh; `timezone=auto` so hours line up correctly regardless of which coordinates were passed in). Defaults to Charlotte, NC when called with no arguments. Has no server-only dependencies, so it's called from both the Header Server Component (the default Charlotte snapshot) and directly from the client (the geolocation snapshot). Returns `null` on any failure so callers can show a quiet fallback instead of crashing.
- `src/components/dashboard/WeatherWidget.tsx` — a Client Component: the compact icon + temp button, and a dropdown panel (high/low + scrollable hourly forecast) that opens on click and closes on an outside click or a second click. On mount, if `window.innerWidth < 768` or the user agent looks mobile, it calls the browser's Geolocation API; on success it re-fetches the snapshot for those coordinates and swaps the panel's location label to "Your location". Desktop skips this check entirely and never touches geolocation. A `weather-geo-permission` flag in `localStorage` (`"granted"` / `"denied"`) remembers the outcome so a past denial is never retried — subsequent mobile loads just stay on the Charlotte fallback without asking again.
- `src/components/dashboard/WeatherWidgetLoader.tsx` — a thin async Server Component that calls `getWeatherSnapshot()` (no args → Charlotte) and passes the result into `WeatherWidget` as `initialSnapshot`. `Header.tsx` renders it inside its own `<Suspense>` boundary (see [Loading States](#loading-states)) rather than awaiting the fetch directly, so a slow Open-Meteo response can't hold up the rest of the header. The date shown next to the title is `HeaderDate.tsx`, a small Client Component — see [Timezones](#timezones) for why that's not computed directly in `Header.tsx`.

Like the Whoop integration, Open-Meteo's response shape is implemented from their public docs and wasn't reachable from this sandbox to verify live (their domain is blocked by this environment's outbound proxy). The mobile/geolocation logic itself was verified with a headless-browser test that mocks `navigator.geolocation` and the Open-Meteo network response — confirmed desktop never calls geolocation, a granted mobile location correctly re-fetches and relabels, and a denied one falls back to Charlotte and stays denied across a reload — but still worth a quick real-device check once deployed.

### Loading States

Every card and both header widgets (Weather, Today at a Glance) now stream in independently behind their own skeleton placeholder, instead of the whole page staying blank until every single fetch — including four external APIs (Whoop, Google Calendar, Todoist, Open-Meteo) — has resolved. Previously `page.tsx` had no `<Suspense>` boundaries at all, so React had to finish building the *entire* render tree, down to the slowest external call, before sending any HTML.

- `src/components/dashboard/Skeleton.tsx` — `Skeleton`, a single `animate-pulse` block (Tailwind's built-in subtle pulse, not a custom gradient-sweep shimmer — no new dependency, and it reads as the same "gray placeholder" idiom used everywhere else), and `WidgetCardSkeleton`, a generic fallback matching "a title plus a handful of list rows": used for Personal Tasks, Habit Streaks, Annual Goals, Routine Cleaning Reminders, and Contacts, the cards whose real shape doesn't need anything more specific.
- `src/components/dashboard/CardSkeletons.tsx` — skeletons shaped to match cards with a more distinctive layout: `TabbedListCardSkeleton` (Work Tasks and Upcoming Events' shared Today/Tomorrow/Upcoming tab row), `HealthCardSkeleton` (the three recovery/sleep/strain stat tiles, the trend chart, and the Weight Tracker goal/log forms beneath), `MealPlanGroceryCardSkeleton` and `WorkoutCardSkeleton` (both cards' two-column layouts), `JournalCardSkeleton` (the textarea plus the condensed button row), and `WeatherSkeleton` / `DailyGlanceSkeleton` (small pills matching each header toggle's resting size, so the header doesn't visibly jump in width once they resolve). Every skeleton that backs a card [Today at a Glance](#today-at-a-glance) can scroll to carries the exact same `id` as the real card, so clicking a glance item while that card is still loading still has something to scroll to.
- `src/components/dashboard/JournalCardLoader.tsx` and `WorkoutCardLoader.tsx` — thin async wrappers that fetch `getJournalEntries()` / `getWorkoutSessions()` and render the existing (Client Component) `JournalCard` / `WorkoutCard` with the result. Both cards previously received their data as props from a `Promise.all` in `page.tsx` itself, which meant page.tsx's own render blocked on them; introducing a small loader wrapper let each get its own `<Suspense>` boundary without having to restructure either Client Component.
- `src/components/dashboard/WeatherWidgetLoader.tsx` — same idea for the header: fetches the Open-Meteo snapshot and renders `WeatherWidget`, wrapped in `<Suspense>` in `Header.tsx` so a slow weather response can't hold up the title, date, or account controls next to it. `DailyGlance` (already its own async Server Component) gets the same treatment — wrapped in its own `<Suspense>` in `Header.tsx` rather than rendered directly, since it aggregates data from five Supabase tables plus Todoist, Google Calendar, and Whoop (see [Today at a Glance](#today-at-a-glance)) and would otherwise be the single slowest thing in the entire header.
- `src/app/page.tsx` — every card is now wrapped in its own `<Suspense fallback={...}>`. The page's own top-level `await` is now just `searchParams` (fast — reads the OAuth-callback query params, not an external call), down from a `Promise.all` that also included the Journal and Workout fetches.
- `src/app/loading.tsx` — Next's route-level loading UI, shown immediately on navigation into the dashboard (most realistically, right after signing in), before `page.tsx`'s own per-card Suspense boundaries take over. It mirrors `page.tsx`'s exact grid using the same skeleton components, so there's no layout shift between this and the real shell.

Verified by inspecting the raw HTTP response stream directly (bypassing the browser, since Playwright's navigation-lifecycle events didn't reliably reflect per-chunk arrival in this sandbox's dev server): three fake cards behind three different artificial delays (200ms/2000ms/3500ms) each had their skeleton in the very first chunk and their real content arrive in a later chunk at almost exactly their own delay, confirming each Suspense boundary resolves independently rather than the page waiting for the slowest one. Also checked in a headless browser for hydration/console errors (none) and confirmed the fully-resolved layout doesn't shift once real content replaces each skeleton, since every skeleton's `className`/`id` mirrors its real card's exactly.

### Today at a Glance

A "Today at a Glance" toggle sits in the header next to the weather widget, using the exact same interaction pattern: click to open a dropdown panel, click again (or click outside) to close it. It summarizes seven categories in one place — Habits, Tasks, Events, Cleaning, Contacts, Meal Plan, and Health — so you can see what needs attention today without scanning every card. Clicking any item scrolls the dashboard straight to that item's card and closes the panel.

- `src/lib/daily-glance-utils.ts` — two small, pure, client-safe functions. `categorizeDueToday(nextDueAt, todayLocalDate)` takes a Cleaning task's or Contact's `nextDueAt` (both share the same shape — an ISO instant, or `null` for one that's never been done/contacted at all) and returns `"due-today"` or `"overdue"` by converting it to a local calendar date and comparing against today; a `null` counts as due today rather than overdue, since there's no established prior due date to call it late against. `isTodoistTaskDueTodayOrOverdue(dueDate, todayLocalDate)` mirrors the Work Tasks card's own "Today" bucket (due today or overdue both count) so the two never disagree about what "today" includes.
- `src/lib/daily-glance.ts` — server-only `getDailyGlanceData()`, which aggregates data by calling the same `getX()` functions every other card already uses (`getHabits`, `getCleaningTasks`, `getContacts`, `getPersonalTasks`, `getTodoistTasksForProjects`, `getUpcomingEvents`, `getMealPlanForWeek`, `getWeightEntries`/`getWeightGoal`, `getHealthSnapshot`) rather than querying tables directly. The tradeoff, since `Header` and `<main>` are sibling Server Components with no shared fetch cache between them, is a second round of the same queries — and, worse, a second live call each to Todoist, Google Calendar, and Whoop — on every page load. Accepted here rather than refactoring every existing card's self-contained data fetching just for this one summary widget, given this is a single-user personal dashboard rather than a high-traffic system. The meal plan portion uses the server's best-guess "this week" (its effectively-UTC clock) rather than adding its own client-side week-correction round trip — the same simplification `MealPlanGroceryCard`'s own initial render already accepts — so a wrong-day meal plan is possible for the few hours right at a week boundary, an acceptable tradeoff for a convenience overview.
- `src/components/dashboard/DailyGlance.tsx` (Server Component, calls `getDailyGlanceData()`) + `DailyGlancePanel.tsx` (Client Component, the toggle button and dropdown panel — `isOpen` state, a `containerRef` for outside-click detection, all copied from `WeatherWidget.tsx`'s exact pattern rather than inventing a new one). Categorization (today's date, which habits are done, which events fall today, etc.) happens entirely client-side, gated behind `useHasMounted()` — a Server Component can't know the user's real local "today" any more than it can for the rest of this app (see [Timezones](#timezones)), so the panel shows "Loading…" for one frame before rendering its actual content.
- Each category always renders, even when empty — "All habits done for today.", "Nothing due today.", "No events today.", "Nothing due or overdue.", "Nobody due for a reach-out." — rather than disappearing, so an empty category reads as a positive status rather than looking broken. Cleaning and Contacts items are explicitly labeled `"<name> - overdue"` or `"<name> - due today"` for every entry (not just the overdue ones), since the request asked for items to be "labeled clearly" and leaving the due-today half unlabeled would read as inconsistent. Personal Tasks have no due date of their own (just a flat running list, unlike Work Tasks), so every outstanding one is treated as "today's" here — there's no other date to filter them by.
- `src/components/dashboard/WidgetCard.tsx` gained an optional `id` prop, and the eight cards this panel links to (Personal Tasks, Work Tasks, Upcoming Events, Habit Streaks, Routine Cleaning Reminders, Contacts, Meal Planning & Grocery List, Health) each pass a fixed id — `personal-tasks-section`, `work-tasks-section`, etc. Clicking a panel item calls `document.getElementById(sectionId)?.scrollIntoView({ behavior: "smooth", block: "start" })` and closes the panel.

### Cross-Card Search

A search button in the header (`⌘K` / `Ctrl+K` from anywhere on the dashboard) opens a command-palette-style dialog that searches across nine of the dashboard's text-heavy sections at once — Personal Tasks, Work Tasks, Habit Streaks, Annual Goals, Routine Cleaning Reminders, Contacts, Grocery List, Journal, and Weight Training — and jumps straight to the matching section. Events, Weather, and Health/Whoop aren't indexed; there's no free text there a search would usefully match beyond what's already visible at a glance.

- `src/lib/search-utils.ts` — pure, client-safe: the `SearchItem` type (`label` is the primary matched/displayed text, `secondary` is optional extra text that counts toward a match but ranks lower — a journal entry's full body when `label` is a truncated preview, a contact's notes, the exercise names inside a workout session), `searchItems(items, query)` (plain case-insensitive substring matching — no fuzzy/typo-tolerant matching or external search library, which would be disproportionate for a single-user dashboard with at most a few hundred items; a stable sort puts label matches ahead of secondary-only matches, e.g. a contact whose *name* matches ranks above one where the term only appears in their notes), and `truncateForLabel(text, maxLength)`.
- `src/lib/search-index.ts` — server-only `getSearchIndex()`, aggregating by calling each feature's own existing `getX()` data layer, the same pattern (and the same accepted "a second round of the same queries, including a second live Todoist call" tradeoff) as `daily-glance.ts` above. A failed fetch (`null`) for any one section just contributes nothing to the index rather than breaking the whole search.
- `src/components/dashboard/GlobalSearch.tsx` (Client Component) + `GlobalSearchLoader.tsx` (Server Component wrapper, same `WeatherWidgetLoader`/`DailyGlance` pattern, its own `<Suspense>` boundary in `Header.tsx`) — a button that opens a centered dialog: results grouped by category (in first-seen order, matching `searchItems`' own rank-then-original ordering within each group), arrow keys to move the keyboard selection, Enter to jump to the highlighted result's section (reusing the same `scrollIntoView` call as the nav rail and "Today at a Glance"), Escape or a backdrop click to close.

Verified end-to-end in a headless browser against a synthetic multi-category fixture: opening via the button and via `⌘K`, the empty-query hint, a query that matches across three different categories with the correct label-before-secondary ranking, arrow-key navigation, Enter jumping to and scrolling the right section then closing the dialog, Escape closing it, and the no-match state.

### Data Export & Backups

Two ways to get your own data out of the app as a single structured JSON file, both built on the same underlying export logic: an on-demand "Export My Data" button in the header, and a fully automatic weekly backup that needs no action from you.

- `src/lib/export.ts` — `buildDataExport(supabase, userId)`, the shared core. Unlike every other data-layer file in this app (`getHabits`, `getContacts`, etc.), it doesn't call `createClient()` itself — it takes an already-constructed client and an explicit `userId` as parameters, because it has to run in two very different contexts: a cookie-bound, RLS-scoped client for the on-demand export, and a service-role client with no session at all (and no RLS to fall back on) for the cron job. Every top-level query filters explicitly on `.eq("user_id", userId)`, which is what actually scopes the data in the service-role case. It queries the app's own stored tables — journal entries, workout sessions (with nested exercises and sets), habits (with completions), personal tasks, the meal plan, grocery items and staples, cleaning tasks (with completions), annual goals (with checkpoints and check-in notes), contacts (with their contact log), and the weight goal and weight entries — and returns one JSON object with a top-level key per section, each section holding its own array(s), children nested under their parent (e.g. a workout session's `exercises`, each with its own `sets`) rather than flattened with foreign keys, so the output reads clearly and could be scripted back into the same tables later if needed. Whoop and Google Calendar connections and Todoist's selected-project preference are deliberately excluded — the first two are OAuth tokens (a security risk to put in a downloadable file, and the underlying health/calendar data itself is pulled live from those services rather than stored here), and the third is a UI preference, not data.
- `src/app/api/export/route.ts` — the manual path. A GET route that checks for a signed-in user via the normal cookie-based client, calls `buildDataExport`, and returns it as `application/json` with `Content-Disposition: attachment`, so a plain link click downloads it directly with no client-side JavaScript needed. Linked from the header via `/data` (see Restore below) rather than directly, now that there's a second thing to do with a backup besides download it.
- `src/lib/supabase/admin.ts` — `createAdminClient()`, a service-role client (`SUPABASE_SERVICE_ROLE_KEY`, never exposed to the browser) for the one context in this app with no user session to read: a scheduled cron invocation.
- `src/app/api/cron/backup/route.ts` — the automated path, invoked weekly by the Vercel Cron Job configured in `vercel.json` (`0 8 * * 0` — Sundays at 08:00 UTC). Checks the `Authorization: Bearer <CRON_SECRET>` header Vercel automatically attaches to real Cron invocations, looks up the (single) user via the admin client's `auth.admin.listUsers()`, builds the export, and uploads it to the private `backups` Storage bucket as `<ISO-timestamp>.json`. Afterward it lists the bucket, and if there are more than 8 files, deletes the oldest ones down to 8 — filenames are ISO timestamps with `:`/`.` swapped for `-`, so sorting them lexicographically is the same as sorting them chronologically. Eight weekly backups is roughly two months of history without accumulating forever.
- `src/lib/supabase/middleware.ts` — the cron route is excluded from the normal "redirect to `/login` if no session" gate (`isCronRoute`), since Vercel invokes it with no cookies at all; its actual authorization is the `CRON_SECRET` check inside the route itself, not a login session.

Verified the export's post-fetch shaping logic (sorting nested exercises by `position` and sets by `set_number`, handling a session with no exercises or an exercise with no sets, defensive against Postgres returning nested rows out of order) and the backup-retention math (deletes exactly the oldest files down to 8, handles fewer-than-8 and out-of-order file listings) against standalone reproductions, since neither `buildDataExport` nor the cron route can run outside a live Supabase project reachable from this sandbox. The manual export button's layout was checked at both desktop and mobile widths in a browser to confirm it doesn't crowd or wrap awkwardly next to the existing Sign Out button.

#### Restore

A backup you can't restore from is only half a safety net, so `/data` (linked from the header as "Data & Backups", replacing the old direct `/api/export` link) pairs the export button above with a restore panel below. Restore is deliberately **per-section**, not whole-backup-at-once — pick exactly which section(s) to restore, so recovering from losing one section's data doesn't mean touching everything else — and each section **replaces** its current data with the backup's rather than merging with it, since these tables mostly have no natural real-world uniqueness constraint to merge on (merging would just create duplicates).

- `src/lib/restore-utils.ts` — a Zod schema per `DataExport` section (mirroring `export.ts`'s row shapes exactly, so a backup this app just produced always validates cleanly), `parseBackupFile()` (checks just the outer `version`/`exportedAt` shape — each section is validated separately, on demand, right before it's restored), `summarizeSection()` (a human-readable count like "3 sessions, 14 exercises, 37 sets" for the confirmation UI), and `SECTION_CAVEATS` (documented exceptions to plain replace — see below).
- `src/app/actions/restore.ts` — `restoreDataSection(section, rawData)`: re-validates the section against its schema (defense in depth — the client already validated the whole file on upload, but this is the actual security/integrity boundary before any write), then for most sections deletes every existing row for the signed-in user and re-inserts the backup's rows verbatim, same ids and all — preserving the exact parent/child structure (e.g. a workout session's exercises and sets) a fresh insert would otherwise have to re-link from scratch. Not wrapped in a database transaction (`supabase-js` can't span one across multiple `.from()` calls without a Postgres function, and writing one felt like overkill for a manual, rare, single-user operation) — if an insert fails partway through, the delete already happened, so the error message says to just try again; the whole delete-then-insert is naturally idempotent since re-running it can't create duplicates.
- **Two sections don't follow plain delete-then-insert**, because their tables were deliberately built to be upserted onto a natural key and never deleted (see their own migrations — neither has a delete RLS policy, on purpose): `mealPlan` upserts onto `(user_id, week_start_date, day_of_week, meal_slot)`, so the backup's values win for any slot it contains but a slot added since the backup isn't removed; the weight goal (part of `weightTracker`) upserts onto `user_id`, and is left untouched entirely if the backup's goal is `null` rather than attempting to clear an existing one. `weightTracker`'s entries, unlike its goal, do have a delete policy and get a normal delete-then-insert. Personal Tasks' due dates aren't in the export at all yet (a pre-existing gap in `export.ts`, unrelated to this feature) — restoring personal tasks won't bring due dates back even if they were set when exported. All three of these are surfaced as an explicit caveat in the restore UI before you confirm, not a silent surprise afterward.
- `src/components/dashboard/DataRestorePanel.tsx` — file picker (parses the JSON client-side via `FileReader`, entirely for fast/friendly feedback — the server independently re-validates regardless) listing all 10 sections with their live counts from the uploaded file; a section with a shape that doesn't validate shows why and disables its button rather than letting you attempt a doomed restore. Clicking Restore doesn't fire immediately — it expands an inline warning (plus that section's caveat, if any) with explicit "Yes, replace my _____ data" / "Cancel" buttons, since this can permanently overwrite real data with no undo beyond restoring yet another backup.

Verified end-to-end in a headless browser against a synthetic multi-section backup file: every section's count summary matches the file's actual contents, a malformed section is flagged and its button disabled, the confirm/cancel flow behaves correctly (confirming shows the warning and caveat text, cancel reverts cleanly), and attempting a real restore against a session-less request fails gracefully with a clear "must be signed in" message rather than crashing — the one thing this couldn't verify from this sandbox is a restore actually landing in a live Supabase project, since none is reachable here.

### Design Consistency Pass

A cross-cutting visual-only audit (no functional changes) across every card, after 12+ sections had accumulated small, independent styling drift from being built incrementally over a long session. Card-level treatment — corner radius, border, background, padding, and the section-title style — was already fully consistent everywhere, since every card goes through the shared `WidgetCard` shell; the actual drift was all in details *within* card bodies:

- **Collapse/expand toggles** (Journal's Entries, Weight Tracker's History, Weight Training's Session History, Annual Goals' Checkpoints & Notes and its nested Check-in Notes, Routine Cleaning Reminders' Recently Completed, Contacts' Recently Contacted): the `▸`/`▾` icon, `flex items-center gap-1.5 text-sm font-medium` label style, and the `border-t ... pt-3` divider immediately above each toggle are now identical everywhere — Annual Goals' two toggles had drifted to `text-xs`, and the divider's own top margin needed to differ slightly by context (`mt-4` when the toggle's parent has no gap of its own, `mt-1` when the parent is already a `gap-3` flex column and only needs a little more separation on top of that) so the *rendered* spacing above each divider ends up the same everywhere rather than just the class names matching superficially. No animation was added to the expand/collapse — none of these ever had one, so they were already consistent in that respect, and adding one now would be a new behavior rather than a style fix.
- **Buttons**: primary (filled) buttons settled into three deliberate size tiers rather than four arbitrary ones — a standalone top-level action (Save Entry, Save Workout, Connect Whoop/Calendar, Add Goal, Save Goal, Log Weight, etc.) is `px-4 py-1.5 text-sm`; an inline "text input + Add button on one row" pattern (Cleaning, Habits, Personal Tasks, Grocery) is `px-3 py-1.5 text-sm` and was already consistent on its own; a compact per-item inline action (Contacts' Save/Log Contact, a goal's Save/Add note) is `px-3 py-1 text-xs`. Secondary (bordered) Cancel buttons paired with a `px-4` primary button are `px-3` — intentionally a touch narrower, not a mismatch — which fixed one outlier (Work Tasks' project-selector Cancel had matched its Save button's width instead).
- **Category/filter pills** (Contacts' category filter, Weight Training's category tabs): both now render at the same `px-3 py-1.5 text-sm`, rather than the filter pills being a size smaller than the tabs for no reason tied to their nearly-identical role.
- **List-item rows** (history entries, goal check-in notes, etc.) already shared one `rounded-lg bg-zinc-50 px-3 py-2 dark:bg-zinc-800/60` treatment almost everywhere; a goal's check-in note rows were the one holdout at smaller padding, now matching.
- **Checkboxes**: all now include `shrink-0` (Personal Tasks' and Work Tasks' were missing it, present everywhere else) so a checkbox can never get compressed in a tight flex row.
- Sub-section headings inside a shared card (Weight Tracker, Grocery List, Weekly Meal Plan — three sections that don't get their own `WidgetCard`, just an `<h3>`) now share the same `mb-3` breathing room below the heading.

Verified with a Playwright-driven preview mounting six representative cards side by side with every toggle expanded at once, at both desktop and phone widths — confirmed no layout regressions (nothing overflows or wraps unexpectedly) and that the toggle dividers, list rows, and button sizing genuinely read as one consistent system now rather than merely sharing class-name strings.

### PWA Support

The dashboard can be added to an iPhone home screen (or installed as a desktop/Android PWA) and launches in standalone mode — no browser address bar — with its own branded icon. No new dependency: every icon is generated at build time from plain JSX/CSS via Next's built-in `ImageResponse`, rather than checking in actual image files.

- `src/lib/app-icon.tsx` — `AppIconMark({ size })`, the one shared visual every generated icon renders (just at different sizes): a rounded-square `#18181b` (zinc-900 — the same token used for every primary button and dark-mode surface elsewhere in the app) background with three white bars, read as a simple "list" glyph — fitting, since the dashboard itself is mostly lists (tasks, habits, cleaning, contacts, ...). It's built entirely from `<div>`s with no text, deliberately — `ImageResponse` renders through Satori, which only reliably supports a basic fallback font unless you explicitly load a font file, and a lettermark risked looking thin or uneven at favicon size.
- `src/app/icon.tsx` (32×32) and `src/app/apple-icon.tsx` (180×180, Apple's recommended home-screen icon size) — Next's file-based icon conventions; each just wraps `AppIconMark` in `ImageResponse` and lets Next auto-generate the correct `<link rel="icon">` / `<link rel="apple-touch-icon">` tags.
- `src/app/icon-192/route.tsx` and `src/app/icon-512/route.tsx` — plain route handlers (not the `icon.tsx` file convention) specifically so they have stable, known URLs — `/icon-192` and `/icon-512` — that `manifest.ts` can reference directly by path, at the two sizes a manifest conventionally needs (192 for standard installed-app display, 512 for high-res/splash use).
- `src/app/manifest.ts` — the web app manifest: `display: "standalone"` is the setting that actually removes the browser chrome on launch; `background_color`/`theme_color` are both the icon's own `#18181b`, which is also what recent iOS Safari (16.4+) fills in behind the icon and name when it synthesizes a home-screen launch screen from the manifest — the closest thing to a custom splash screen achievable without hand-building a startup-image file for every individual iPhone/iPad screen size (the older, high-maintenance approach `appleWebApp.startupImage` supports but this app doesn't use).
- `src/app/layout.tsx` — added a `viewport` export with `themeColor` (light/dark variants matching the header's own `bg-white` / `dark:bg-zinc-950`, so browser chrome doesn't visibly mismatch the app while it loads), and to `metadata`: `appleWebApp` (sets the home-screen title and a `black` status bar — opaque, not `black-translucent`, since translucent draws content edge-to-edge under the status bar and this app has no safe-area-inset padding to keep the header clear of a notch) and `other: { "apple-mobile-web-app-capable": "yes" }`. That last one is set explicitly rather than left to Next's default `appleWebApp` output — Next only emits the modern, unprefixed `mobile-web-app-capable` tag, but iOS Safari has historically only honored its own vendor-prefixed version for actually launching in standalone mode from a home screen icon, which is the specific behavior this feature is for.
- `src/lib/supabase/middleware.ts` — the five new icon/manifest routes (`/icon`, `/apple-icon`, `/icon-192`, `/icon-512`, `/manifest.webmanifest`) needed their own exclusion from the auth-gating redirect, alongside `/privacy` and `/api/cron`. They're extension-less URLs, so they didn't already match the proxy matcher's file-extension skip list — without this, the browser/OS fetching them with no session (exactly what happens the first time someone tries to add the app to their home screen) would get silently redirected to `/login`, breaking the icon and installability outright. Caught by testing the routes directly rather than just eyeballing the code.

Verified by starting a dev server and fetching each route directly: all five return `200` un-authenticated (confirming the middleware fix), the manifest JSON parses with the expected fields, all four generated PNGs decode at their exact intended dimensions (32×32, 180×180, 192×192, 512×512) and are legible at every size down to the 32px favicon, and the real `<head>` output on a live page includes every expected tag — both theme-color variants, the manifest link, both the modern and legacy web-app-capable meta tags, the apple-mobile-web-app-title and status-bar-style tags, and the new icon/apple-touch-icon links.

#### Offline Support

Before this, "installed" meant an icon and a splash screen but zero actual resilience — opening the app with no signal (relevant for a dashboard someone travels with) just failed with the browser's own generic network-error page. A hand-written service worker now gives real offline behavior, without any build plugin or Workbox dependency — deliberately small and easy to fully audit given how much blast radius a service worker has (it can intercept every same-origin request the page ever makes).

- `public/sw.js` — precaches the `/offline` fallback page plus the two icon routes at install time (fetched and cached individually, not via `cache.addAll`, so one transient failure can't silently take down the whole precache — the `/offline` page landing in the cache is what actually matters). Its `fetch` handler only ever touches same-origin `GET` requests — anything else (Server Action `POST`s, Supabase's own cross-origin calls, OAuth redirects) is left completely alone by simply never calling `respondWith()`. Within that: **page navigations always go to the network first** and are never served from a cache — this dashboard is fully dynamic, per-user, authenticated content, and a stale or wrong-session snapshot would be actively misleading (yesterday's habits shown as today's, a completed task still shown outstanding); the cached `/offline` page is used *only* when the network request itself fails outright. **Static, content-hashed build assets** (`/_next/static/*`, the icon/manifest routes) use cache-first, which is safe specifically because a given URL's content never changes for those. Everything else (API routes, RSC data fetches) falls through to the network untouched, never cached.
- `src/app/offline/page.tsx` — the fallback itself: a plain, static, no-data page (matching the splash screen's own minimal dark-theme visual language) served straight from Cache Storage with no network round trip when a navigation fails. Its "Try Again" link is a deliberate plain `<a>`, not `next/link` — `Link` performs a client-side transition (an RSC data fetch, not a real browser navigation), which the service worker's `request.mode === "navigate"` check wouldn't catch, silently breaking the retry.
- `src/components/ServiceWorkerRegister.tsx` — a `"use client"` no-render component mounted once in the root layout (alongside `AppSplashOverlay`) that calls `navigator.serviceWorker.register("/sw.js")` on mount, regardless of auth state. A registration failure (an unsupported browser, or a sandboxed context that blocks service workers) is silently ignored — this is a progressive enhancement on an app that already works fully without one.
- `src/lib/supabase/middleware.ts` — both `/sw.js` and `/offline` needed their own exemption from the auth-gating redirect. `/sw.js` has a `.js` extension not covered by the proxy matcher's image-extension skip list, so an unauthenticated fetch (the browser's own periodic service-worker update check, or registration from an unauthenticated `/login` visit) would otherwise get redirected to `/login` — and since the service worker's own install-time precache fetch has no session either, `/offline` needs the same exemption so the *real* offline page gets cached, not a login-page redirect.

Verified two ways. End-to-end in a real browser: visiting a page registers and activates the service worker, and the three precache URLs genuinely land in Cache Storage. The actual offline-fallback *logic*, though, needed a different approach — Playwright's `context.setOffline()` didn't reliably reach the service worker's own separate execution target (a known CDP limitation: the emulated "offline" network condition applies to the page's target, not necessarily a Service Worker's own background one), so a real-browser "go offline, navigate, check the page" test couldn't actually prove the network-failure branch runs — it only proved the *page's* network was offline, not that the service worker's *own* internal `fetch()` call was blocked. Loading the real `public/sw.js` file directly in a sandboxed context (Node's `vm` module) with a controllable fake `fetch` sidesteps that limitation entirely and verified all of it directly: precache resilience to a partial failure, the offline-fallback branch actually firing when the network fetch rejects, the online branch correctly returning the live response without caching it, cache-first behavior for static assets (fetched once, served from cache on the second request with no second fetch), and that non-GET and cross-origin requests never get intercepted at all.

#### Push Notifications

A daily reminder (Settings → Notifications, `/data`) for anything still outstanding — habits not yet checked off, contacts due for a reach-out — sent once a day at a fixed time regardless of whether the app is even open. Deliberately silent when nothing is due: a notification that says "nothing to do today!" every day trains you to ignore it, so `buildDailyReminderContent` returns `null` and the cron simply doesn't send anything.

- `supabase/migrations/20260817000000_create_push_subscriptions.sql` — `push_subscriptions` table (one row per subscribed browser/device, so the same account can get reminders on both a phone and a laptop), holding the push service `endpoint` plus the `p256dh`/`auth` encryption keys Web Push requires. RLS scoped to `auth.uid() = user_id` for select/insert/update/delete — the update policy matters as much as insert, since re-subscribing from the same browser (after a permission reset or a redeployed VAPID key) upserts onto `unique (user_id, endpoint)` rather than erroring.
- `src/lib/push-utils.ts` — `urlBase64ToUint8Array()`, the standard conversion from the VAPID public key's base64 string form to the raw `Uint8Array` `PushManager.subscribe()`'s `applicationServerKey` requires.
- `src/lib/push-notification-content.ts` — `buildDailyReminderContent(habits, todayLocalDate, contacts)`, the pure function deciding what the reminder says (or whether it sends at all), reusing the same `isContactVisible`/due-habit logic the dashboard cards themselves already compute from — the notification and the card can never disagree about what's actually due.
- `src/app/actions/push.ts` — `subscribeToPush()` (upserts the browser's subscription for the signed-in user) and `unsubscribeFromPush()` (deletes it), both auth-gated the same way every other Server Action in this app is.
- `src/app/api/cron/push-reminders/route.ts` — the sending side, invoked daily by the Vercel Cron Job in `vercel.json` (`0 12 * * *`, chosen to land in the morning for an Eastern-US-based user — the same assumption `WeatherWidget`'s desktop default already makes, since nothing in this single-user app stores an actual timezone). Same `CRON_SECRET` bearer-token check as the existing backup cron, same single-user `auth.admin.listUsers()` assumption, same admin/service-role client for the no-session context. Loads every subscription plus enough habit/contact data to compute today's status, builds the reminder content, and sends via `web-push`'s `sendNotification()` to each subscription — a 404/410 response from the push service means that subscription is dead (browser data cleared, app uninstalled), so it's deleted rather than retried forever.
- `public/sw.js` — added `push` and `notificationclick` listeners alongside the existing offline-support ones. `push` parses the notification payload as JSON (falling back to plain text if that fails, so a malformed payload degrades gracefully instead of silently dropping the notification) and calls `registration.showNotification()`. `notificationclick` focuses an already-open dashboard tab if one exists rather than always spawning a new one.
- `src/components/dashboard/NotificationSettings.tsx` — the Settings-page toggle: checks `Notification.permission` and any existing `PushSubscription` on mount, and on enable, requests permission, subscribes via `PushManager.subscribe()`, and saves the subscription server-side — rolling the browser-side subscription back with `.unsubscribe()` if the server save fails, so the two never end up out of sync. Renders "not configured" when no VAPID key is present (e.g. a fork that hasn't set one up) rather than a broken button.
- `src/app/data/page.tsx` / `src/components/dashboard/Header.tsx` — the page (still at `/data`, only its URL now undersells what's there) gained a "Notifications" section ahead of Export and Restore, and its header link/title were broadened from "Data & Backups" to **Settings** to match.

Verified with the full automated suite (unit tests for `push-utils` and `push-notification-content`, `eslint`, `tsc`/production build) plus a `vm`-module test mirroring the offline-support technique above: the real `public/sw.js` source is loaded into a sandboxed context with mocked `self`/`caches`/`clients` globals, and its actual `push`/`notificationclick` listeners are invoked directly — asserting a well-formed JSON payload shows a notification with the right title/body/tag, a malformed payload falls back to plain text instead of throwing, a `data`-less push still shows a fallback notification, and `notificationclick` focuses an existing tab when one is open and opens a new one when none is. End-to-end delivery through a real push service couldn't be exercised in this environment (no live VAPID keys or authenticated Supabase session available here), so that step is left for a real deployment with `NEXT_PUBLIC_VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` configured.

### Jump-to Navigation Rail

A persistent way to jump straight to any of the 12 dashboard sections, without needing to open Today at a Glance first. Reuses that feature's own scroll-to-section mechanism (`document.getElementById(id)?.scrollIntoView({ behavior: "smooth", block: "start" })`) rather than inventing a second one.

- `src/lib/use-active-section.ts` — `useActiveSection(ids)`, a scroll-spy hook built on `IntersectionObserver` (watching a thin horizontal band 15% down from the top of the viewport, so the section whose top has just crossed that line is the one considered "current") that returns whichever section id is currently in view. Cards stream in behind their own Suspense boundaries and can replace a section's DOM node (skeleton → real content, same `id`) after the hook's first render, so a plain one-time `observe()` would silently go stale for any card that hadn't finished loading yet. Instead it tracks a `Map<string, HTMLElement>` of the node currently being observed per id, and re-syncs every 400ms for the first 20 seconds after mount — long enough for every card to have settled, short enough not to poll forever — re-observing only when `document.getElementById(id)` returns a different node than last time.
- `src/components/dashboard/NavRail.tsx` — the 12-section list (in the same order the cards appear in `page.tsx`) rendered two different ways depending on viewport, both mounted at all times and switched with `hidden xl:block` / `xl:hidden` (matching the breakpoint-based show/hide pattern already used elsewhere, e.g. `Header.tsx`'s email) so there's no server/client hydration mismatch from only rendering one at runtime:
  - **Desktop** (`xl:`, 1280px, and up only): a `position: fixed`, vertically-centered column of small dots — no background, border, or shadow box around them, and no hover-to-expand state. An earlier version pinned the rail to the literal viewport edge and grew a labeled box on hover, which at typical desktop widths overlapped card content instead of sitting beside it — the page's own `max-w-6xl` (72rem) content column leaves too little true margin outside itself for that to ever work cleanly. This version positions the rail with `left-[calc(50%-39rem)]`, relative to the viewport's horizontal center rather than its edge, so it tracks the content column and keeps a fixed 1rem gap in front of it at every width — verified to hold a clean ~50px+ gap in practice from 1280px up. It's gated behind `xl:` rather than `lg:` (1024px) specifically because at 1024–1279px that gap math goes negative — there's no safe margin left for a rail at all, so those widths fall through to the mobile treatment instead. Labels are a native `title` tooltip plus an `aria-label`, not a custom overlay — nothing to obscure content with.
  - **Below `xl:`** (phones through 1279px-wide laptops): a small floating action button fixed in the bottom-right corner instead, since a sidebar would eat too much of a screen that narrow either way. Tapping it expands a compact list of the same 12 links above it; tapping a link scrolls to that section and closes the list. Open/close and click-outside-to-close are the exact same `isOpen` + `containerRef` + document `mousedown` listener pattern `DailyGlancePanel.tsx` already uses, not a new one.
  - Both variants highlight the active section (`aria-current="true"`) using the same `useActiveSection` call, so scroll position and the two navs never disagree about "where you are."

Verified with a Playwright-driven preview page rendering all 12 sections as tall, easily distinguishable blocks, across five widths (1024, 1152, 1280, 1440, 1920px) and a 390px phone width: below 1280px only the floating button renders (confirming no dead zone between the old and new breakpoints); at 1280px and up, the rail renders as a plain column of dots with a measured, consistent 50px+ gap between the rail and the nearest card, unchanged by hovering it (confirming the removed expand-on-hover state can't reintroduce an overlap); clicking any item smooth-scrolls to the matching section and the corresponding dot is marked `aria-current` once scrolling settles; scrolling back to the top re-highlights the first section; and on mobile, the floating button opens/closes its panel on tap and on an outside click, same as before.

### Category Color Coding

A subtle accent — a 4px colored left border on top of each card's existing 1px border — groups the 12 dashboard sections into five life areas, so the dashboard is scannable by category at a glance rather than only by reading each title:

- `src/lib/section-category.ts` — the single source of truth: a `SECTION_CATEGORIES` map from each section's `id` (the same id already used for scroll-to-section and the nav rail) to one of five categories, and a `getSectionAccentClass(id)` helper returning that category's Tailwind classes. Health/Fitness (Health, Weight Training) is emerald, Personal Growth (Journal, Annual Goals, Habit Streaks) is violet, Home/Life (Routine Cleaning Reminders, Meal Planning & Grocery List) is amber, Productivity (Personal Tasks, Work Tasks, Upcoming Events) is sky, and Relationships (Contacts) is rose. Habit Streaks wasn't part of the original category groupings suggested for this feature — placed here (Personal Growth) after asking rather than guessing at a personal categorization preference.
- `src/components/dashboard/WidgetCard.tsx` calls `getSectionAccentClass(id)` and appends the result to its existing className string — every one of the 12 sectioned cards already passes its own `id` for the nav rail and Today at a Glance, so no other card file needed to change. The colors are all soft mid-tones (`-400` in light mode, a slightly deeper `-600` in dark mode) rather than saturated, and the accent is a single 4px strip rather than a filled background or icon change, so it reads as one consistent, restrained system rather than a rainbow.
- The Suspense-fallback skeletons (`WidgetCardSkeleton` in `Skeleton.tsx`, and `TabbedListCardSkeleton`/`WorkoutCardSkeleton`/`JournalCardSkeleton` in `CardSkeletons.tsx`, all of which already receive the real card's `id`) call the same `getSectionAccentClass(id)` helper, so a card's accent color is present from the very first paint rather than popping in only once the real content streams in.

Verified with a Playwright-driven preview page rendering all 12 real `WidgetCard`s side by side and screenshotting both light and dark color schemes: each card shows a left-edge accent in the correct category color, colors are visually distinct from one another at a glance without being harsh, and the per-side border-color override (`border-l-4 border-l-{color}` layered on top of the shared `border border-zinc-200`/`dark:border-zinc-800`) renders as intended in both themes with no leftover default-gray edge peeking through.

### Progress Chart Readability

The Weight Training progress chart plotted its estimated-1RM line with no way to actually read the values off it — no Y-axis scale, and tooltips existed only in code, not in any form a touchscreen could trigger. All three gaps are in `src/components/dashboard/ProgressChart.tsx`:

- **Y-axis** — a new `getYAxisTicks(dataMin, dataMax, tickCount)` helper generates 4 evenly-spaced gridline values rounded out to the nearest 5 lb (how plates and dumbbells actually increment), rather than the raw, oddly-specific min/max Epley's formula happens to produce for a given session — e.g. `210 / 220 / 230 / 240` instead of `213 / 238`. When every point in the series has the same value (a single logged session, or several sessions tied at the same 1RM), min equals max and there's no range to divide into ticks; that case pads a small window around the single value first so the axis still renders a real scale instead of one degenerate line. The existing point-plotting math was switched from scaling against the raw data min/max to scaling against this axis's own min/max, so points still land in the correct place relative to the now-visible gridlines.
- **Tooltips** — the hover tooltip already existed but only had `onMouseEnter`/`onMouseLeave` handlers, which a touchscreen never fires on its own. Each point now has a second, larger (12px radius vs. the visible 4px dot) invisible hit-target circle with an `onClick` handler, so a tap registers even without landing exactly on the tiny dot first; clicking/tapping anywhere else on the chart's background clears it. Testing this surfaced a real bug before it shipped: touch (and Playwright's own `.click()`) synthesizes a `mouseenter` immediately before the `click` event, so an initial "toggle on click" implementation opened the tooltip via the synthetic hover and then immediately closed it again via the toggle — on every single tap. Fixed by having the click handler unconditionally set the hovered index rather than toggle it. Testing also caught a second, pre-existing bug unrelated to touch: the tooltip for a point near the chart's right edge rendered as a squeezed, multi-line box instead of one line — a CSS quirk where an absolutely-positioned, auto-width element's "shrink-to-fit" sizing only has a sliver of space to work with when its `left` sits close to 100%, so it wraps instead of using its natural width. Fixed by anchoring the tooltip from its own left or right edge (instead of always centering it) whenever the point is within 15% of either end of the chart.
- **Start → current summary** — a plain-text line above the chart (`225 lb → 245 lb`, with a small `(+20 lb)` in emerald or a `(-lb)` in red alongside it, or plain zinc text if unchanged) reads the very first and very last point already computed for the chart, so progress is visible without needing to hover or tap at all. A session log with only one data point shows `Current: 245 lb` instead, since there's no "start" distinct from "current" to show an arrow between.

Verified with a Playwright-driven preview page using synthetic session data (a six-session upward trend, plus a single-session category to exercise the flat-range axis case): the Y-axis renders four nicely-rounded gridline labels; hovering a point shows its exact date and value in one line, confirmed specifically at the rightmost point where the wrap bug used to appear; tapping (via `.click()`) shows the same tooltip and stays open, where before the fix it opened and immediately closed; tapping the chart background dismisses it; and the summary line reads correctly for both the multi-point and single-point cases, in both light and dark color schemes.

### Mobile Layout Fixes

Two small mobile-only issues, unrelated to each other beyond both being mobile-specific:

- **Header congestion** — with the user's email, Today at a Glance, Export My Data, and Sign Out all competing for space, the header felt cramped on narrow screens. `Header.tsx`'s "Export My Data" link now has `hidden sm:inline-block`, matching the same breakpoint-based pattern already used for the email next to it. The export is still directly reachable at `/api/export` — this only removes the button, not the capability.
- **Horizontal page scroll** — the dashboard could scroll sideways on mobile. A background audit agent searched every card component for common causes (fixed pixel widths, unwrapped tables, `w-screen`, negative margins, unbounded flex rows) and flagged two candidates: `WeightTrendChart.tsx`/`RecoveryTrendChart.tsx`'s hover tooltips (which share `ProgressChart.tsx`'s pre-fix centering logic — see [Progress Chart Readability](#progress-chart-readability) above — but hadn't received that same fix), and three list rows (`TasksCardBody.tsx`, `EventsCardBody.tsx`, `PersonalTasksCardBody.tsx`) missing the `min-w-0`/truncation pattern every comparable row elsewhere in the app already uses. Both got fixed, but only one turned out to be the actual cause of a real, page-wide scrollbar — worth recording since the more visually obvious lead wasn't the real bug:
  - The tooltip fix (same edge-aware `left`/`right`-anchoring as `ProgressChart.tsx`, applied to the other two trend charts for consistency) turned out **not** to cause real page overflow when checked directly — an absolutely-positioned, auto-width box's CSS "shrink-to-fit" sizing has no room to grow past its container in this exact layout, so it squeezes down and wraps ugly rather than actually spilling past the viewport edge. Still worth fixing for the visual bug and for consistency with `ProgressChart.tsx`, just not the culprit here.
  - The list-row fix **is** confirmed as the real cause, reproduced directly: a flex row's text child defaults to `min-width: auto` (a floor equal to its longest unbreakable "word"), so ordinary multi-word text always wraps fine, but one genuinely unbroken long token — a pasted URL, a long slug, the kind of content a Todoist task, personal task, or calendar event title can plausibly contain — can't wrap and pushes the row (and the whole page) wider than the viewport. Fixed with `min-w-0` (lets the flex item shrink below that floor) plus `break-words` (lets the browser break the long token mid-word once it has room to) on `task.content`/`event.title` in the three flagged files — deliberately not `truncate`, which would also clip perfectly normal, currently-working multi-line task and event text down to one line.

Verified by reproducing the actual bug before trusting the fix: a Playwright preview page rendered the exact same list-row markup with a deliberately long unbroken string, once with the original classes and once with the fix. The unfixed version measured `document.documentElement.scrollWidth` at 696px against a 375px viewport (visibly spilling off-screen in a screenshot) — reproducing the reported bug; the fixed version wrapped the same string cleanly within the card and measured no overflow at all. The same scrollWidth-vs-viewport check, run against the two trend charts with their rightmost point hovered at five phone widths (320-414px), confirmed they don't contribute any overflow either before or after their own tooltip fix.

### Habits: Hide Once Done Today

A habit now drops out of the main Habit Streaks list the moment it's checked off for the day, and reappears the next day ready to check off again — a display-only change in `HabitsCardBody.tsx`, entirely separate from the underlying data:

- `visibleHabits`, a filtered view (`localHabits.filter((h) => !h.completedDates.includes(today))`) computed alongside the existing `today`, is what actually gets rendered. `computeHabitStreaks` and `getChainCalendar` are still called on each full `habit` object exactly as before — nothing about how "current," "best," or the chain-calendar dots are computed changed, so a habit that disappears today and reappears tomorrow shows precisely the streak and history it would have shown had it never been hidden. Checking a habit off already updated `completedDates` optimistically before this change; filtering on that same array is what makes it vanish the instant it's checked, with no new state or effect needed.
- The up/down reorder buttons' disabled state (previously just the map's own `index === 0` / `index === length - 1`) now derives a `fullIndex` via `localHabits.findIndex(...)` instead, since `index` from mapping over the filtered `visibleHabits` would otherwise disable "move up" on whichever habit happens to be first *among the currently-visible ones* rather than genuinely first in the full, saved order.
- Three empty-ish states, distinguished explicitly rather than collapsed into one: no habits ever added ("No habits yet — add one above."), at least one habit exists but every one is done today ("All habits done for today." — the new case), and (unchanged) the pre-mount loading flash.

Verified with a Playwright-driven preview using synthetic habits, including one with a real two-day completion history ending yesterday (not yet done today): it renders visibly with its correct `🔥2 · best 2` badge untouched, confirming the streak math is fully independent of the new visibility filter. A habit already marked done for today is correctly absent from that same initial render. Checking a still-visible habit's box hides it immediately. A card whose only habit is already done for today renders "All habits done for today." on first load rather than an empty list.

### Cleaning Reminders: Fixed Weekly (Sunday) Scheduling

Routine Cleaning Reminders switched from a rolling interval (due N days after it was last completed — 7/14/30 for weekly/biweekly/monthly, drifting later every time a task got done late) to a fixed, calendar-anchored schedule: every task is due on a Sunday, and completing it late never shifts that schedule. All the new logic lives in `src/lib/cleaning-utils.ts`, replacing `computeCleaningStatus`'s old elapsed-time math entirely:

- **The schedule is pure calendar math, never completion history.** A private `isDueWeek(frequency, sunday)` decides whether a given Monday-Sunday week is a due week: weekly is every week; biweekly is every other week, alternating off a fixed reference Sunday (`2024-01-07`) shared by every biweekly task, rather than each task drifting onto its own rhythm based on when it happened to be created or last done; monthly is whichever week contains the first Sunday of the month. `findActiveDueSunday` walks backward (bounded at 5 weeks — comfortably more than monthly's worst case) from the current week to find the most recent due week, so a biweekly/monthly task in an "off" week still correctly resolves to its last real deadline rather than losing track of it.
- **A task stays actionable (`isDue`) for its entire due week** — Monday through Sunday — not just on Sunday itself, so "completed any day within its due week" (as specified) is satisfied by checking whether the latest completion falls on or after that due week's own Monday. It stays `isDue` (now overdue) indefinitely past that Sunday, across any number of further off-weeks, until it's actually done — a missed biweekly/monthly task doesn't just silently disappear when its week ends.
- **`isHidden`** is true only through the remainder of the due week it was just completed in, becoming false again starting the very next Monday — a fixed one-shot grace window, not a multi-week hide for biweekly/monthly. One real nuance surfaced while designing this and confirmed with the user rather than assumed: for **weekly** tasks specifically, since every week is a due week, there's no gap at all between "reappears Monday" and "due again" — a weekly task reappearing Monday is immediately `isDue: true` for the new week (not a countdown), whereas biweekly/monthly tasks genuinely do reappear in a not-yet-due, counting-down state until their next due Sunday, since their next due week is often weeks away.
- `daysSinceCompleted` is gone (no longer a meaningful concept under a fixed schedule); `nextDueAt` keeps its existing dual meaning — the active overdue/due deadline while `isDue`, otherwise the next upcoming due Sunday — so `daily-glance.ts`/`DailyGlancePanel.tsx`'s existing `categorizeDueToday(task.nextDueAt, today)` call needed no changes at all.
- Like Habit Streaks' streak math, due-status now depends on the local calendar day (a Sunday/Monday boundary is a real-timezone concept), so `CleaningCardBody.tsx` recomputes it client-side after mount from each task's raw `frequency`/`lastCompletedAt`, the same pattern `HabitsCardBody` already uses for streaks — rather than trusting whatever the server precomputed with its own clock. `cleaning.ts`'s server-side `getCleaningTasks()` still precomputes a status object too (using the server's own local date as a best-effort guess, the same accepted tradeoff `getDailyGlanceData`'s meal-plan lookup already makes), since Today at a Glance consumes that value directly without its own recomputation — only the primary card needed to become fully client-accurate.
- `CleaningCardBody`'s main list now only ever shows tasks not yet done for their current cycle, so checking one off always means "mark done now" — never an undo/uncheck as the old rolling-interval version supported for a brief window. The checkbox in the main list is now unconditionally unchecked rather than reflecting `!isDue`, since anything shown there is, by construction, not yet satisfied.
- The old 7-day "coming up soon" visibility window is gone — every not-yet-due task now stays visible in the main list with a countdown (`next due Sun, Aug 23 (in 17d)`) rather than being hidden until close to its deadline, since the new spec calls for the main list to show everything except the specific just-completed/waiting-for-Monday state.

Verified two ways. First, a standalone script (run via `node --experimental-strip-types`, mirroring how the habit-streak algorithm was verified earlier) exercised `computeCleaningStatus` directly across 24 cases spanning all three frequencies — due/overdue/hidden/reappeared transitions, an off-week for biweekly and monthly correctly walking back to the right prior due Sunday, and the weekly "immediately due again" edge case once confirmed with the user. Second, a Playwright-driven browser preview confirmed the same behavior end-to-end: a never-completed task shows "Due now — never done"; a task already completed this week is correctly absent from the main list and shows "Next due Sun, [date]" under Recently Completed; checking off the last remaining visible task immediately shows "All cleaning tasks are done for the week — they'll reappear Monday."

### Optimistic UI Audit

A pass across every checkbox, toggle, and quick-action on the dashboard — Habit Streaks, Routine Cleaning Reminders, Personal Tasks, Work Tasks, Contacts, Grocery List, Weight Training, Journal, Annual Goals — checking each one against this app's established optimistic pattern: mutate local state immediately (before the server call), run the actual save in `startTransition`, and call `router.refresh()` unconditionally afterward so a failure quietly reverts the optimistic change once the real server state comes back. A background audit agent found 31 interactive handlers total; 27 already followed the pattern correctly. Three genuinely didn't, all fixed here:

- **`WorkoutCard.tsx`'s "Save Workout"** — the filled-in form (name, category, exercises) sat untouched, and the new session didn't appear in Session History or the progress chart, until the server round-trip finished. Now it constructs an optimistic `WorkoutSession` (a temporary `optimistic-<timestamp>` id, following the same synthetic-id convention `GroceryListSection`'s quick-add and `GoalItem`'s add-note already use) and prepends it to `localSessions` immediately, clearing the form in the same tick. Since a failed save here would otherwise mean the user has to retype an entire logged workout — a meaningfully worse loss than a reverted checkbox — the error path goes further than the usual "show an error and let refresh reconcile": it explicitly restores the exact name/category/exercises the user had typed and removes the optimistic session, a real revert rather than a refetch-and-hope.
- **`TasksCardBody.tsx`'s Todoist project-picker "Save"** — closed the picker only after the save confirmed. Now it closes immediately (the selection the user checked is already fully known client-side, so there's nothing left to wait on) and reopens the picker with the same selection intact if the save actually fails, surfacing the error right there for an easy retry.
- **`MealPlanSection.tsx`** had two separate gaps: `persistEntry` (backing every meal-mode/content/leftover edit) never called `router.refresh()` at all, meaning a failed save left the optimistic edit permanently wrong with no way to reconcile — now it does, unconditionally. `handleAddParsedItems` ("Add to Grocery List" after AI-parsing ingredients) waited for the round-trip before closing the ingredient panel; it now closes immediately, with a new top-level `groceryAddError` banner to surface a failure after the inline panel that would have shown it is already gone.

Two handlers the audit flagged were deliberately left as-is, not overlooked: `handleCopyPreviousWeek` and `handleStartParse` (AI ingredient parsing) both need data the client doesn't have yet — the actual previous week's entries, or the LLM's parse result — so there's no locally-known target state to render optimistically; a brief "Copying…"/"Parsing…" state is the correct, unavoidable UX for a genuine fetch, not a violation of the optimistic-UI pattern.

Verified by exercising both fixes in a Playwright browser preview against the real (session-less, so guaranteed-to-fail) server actions: for Weight Training, filling in a session and clicking Save cleared the form and bumped Session History from (1) to (2) within 30ms of the click, then — once the expected "You must be signed in" error came back — restored the typed name and dropped the count back to (1); for Work Tasks, clicking Save on a changed project selection closed the picker immediately, then reopened it with the error message and the same checkboxes still checked once the save failed.

### Drag-to-Reorder Dashboard Sections

Every top-level section now has a small six-dot grip (⋮⋮) in its header, next to the title, that lets you press-and-drag to reorder sections directly on the normal dashboard — no separate edit mode, and the order is remembered per user via a new `dashboard_section_order` table (`user_id` primary key, RLS-scoped, a `text[]` column holding the ordered section ids — the same single-row-per-user shape `todoist_preferences` already uses).

- **Only the handle drags, not the whole card.** Built on `@dnd-kit/core`/`@dnd-kit/sortable` (a headless, handle-friendly, touch-and-keyboard-capable drag-and-drop library — nothing like this existed in the app already, and hand-rolling pointer-based reordering across a responsive multi-span CSS Grid would have meant reimplementing a lot of what a maintained library already gets right). The grip button is the only element with drag listeners and `touch-action: none`; the rest of each card keeps its normal scroll/tap/click behavior untouched, which matters most on mobile where a card-wide drag zone would otherwise fight the page's own scroll gesture.
- **The grid's column-spanning survives reordering untouched.** `AnnualGoalsCard`, `JournalCard`, `MealPlanGroceryCard`, and `WorkoutCard`'s `lg:col-span-*` classes live directly on WidgetCard's own `<section>` — the actual CSS Grid item — same as before this feature. `SectionOrderBoard.tsx`'s `DndContext`/`SortableContext`/context-provider wrapper renders no DOM element of its own, so nothing new sits between `<main className="grid ...">` and each card's `<section>` that could break `grid-column: span`.
- **A single `useSortable()` call per section, shared via context.** `SortableSectionProvider` calls `useSortable({id})` once per section and provides the result through a `SectionSortableContext`; `WidgetCard` reads it to attach `setNodeRef`/the drag transform to its own `<section>`, and a `DragHandle` sub-component reads the same context directly (rather than receiving it as a prop) to wire up `listeners`/`attributes`/`setActivatorNodeRef` on the grip button — reading it in the same component that attaches it to a DOM node, not threading it through props, is what keeps React's ref-safety checks happy.
- **`DndContext` is given a stable, explicit `id`** (`dashboard-section-order`) — dnd-kit auto-generates an internal id used for an ARIA live-region otherwise, and that internal counter increments differently between the server render and the client's first render, producing a real (if harmless) hydration-mismatch warning; an explicit id sidesteps it entirely, which is dnd-kit's own documented fix for SSR frameworks.
- **Saving is fire-and-forget, not the usual revert-on-failure pattern.** `saveSectionOrder` (a new server action) upserts the order and deliberately skips `revalidatePath` — unlike this app's other actions, since there's no server-rendered output tied to section order for the page to catch up on, and revalidating would force every other card to refetch its data (including external Todoist/Whoop/Google Calendar calls) for a change that's already fully reflected in the client's own state. On save failure, the reorder is kept as-is (there's no reason to discard a deliberate drag just because the DB write failed) and a small dismissing toast explains the order won't persist past this page load.
- **A saved order merges with the current section list** via `resolveSectionOrder()` in the new `dashboard-sections.ts`: known saved ids keep their relative order, and anything missing — a new section shipped after the user last reordered, or a stale id — is appended at the end in its default position, so this never drops or duplicates a section.

Verified with a Playwright preview (a temporary `dev-section-order-preview` page, cleaned up afterward) using both mouse and simulated touch input: dragging a card by its handle reorders it and persists optimistically; dragging from anywhere else on a card (its scrollable body) does nothing to the order and leaves normal scrolling intact; a `lg:col-span-3` test section kept its full triple-width span throughout. The jump-to Nav Rail was deliberately left showing sections in their fixed original order rather than syncing to the custom order — the request was specifically about the cards' own layout, and wiring two independent client components together to share live order state was more machinery than the ask called for.

### Global Error and Offline Handling Audit

A pass across every section that depends on an external service (Whoop, Google Calendar, Todoist, Open-Meteo) and every core Supabase-backed section, checking that a failure anywhere degrades gracefully instead of breaking silently or taking the rest of the dashboard down with it. This surfaced two real, structural gaps beyond what a per-card look would have caught:

- **A Supabase error was indistinguishable from "genuinely nothing here."** `getHabits`, `getPersonalTasks`, `getContacts`, `getCleaningTasks`, `getJournalEntries`, `getAnnualGoals`, `getWeightEntries`, `getMealPlanForWeek`, `getGroceryItems`, `getGroceryStaples`, and `getWorkoutSessions` all caught their Supabase error and quietly returned `[]` — the exact same shape as a real empty state. A database outage would have shown "All habits done for today!" or "No cleaning tasks — you're all caught up," confidently wrong rather than visibly broken. Every one of these now returns `null` specifically on error (kept distinct from an empty array), mirroring the `T[] | null` convention `getTodoistProjects`/`getUpcomingEvents`/`getHealthSnapshot` already used for exactly this reason. Each card now branches on `null` to show a new shared `SectionLoadError` (a calm message plus a `RetryButton` that calls `router.refresh()` — a background re-fetch, not a full page reload) instead of falling through to its normal empty-state copy. Where a card mixes reading history with writing new data (Journal, Weight Tracker, Weight Training, Meal Planning, Grocery), only the affected list/history shows the load error — composing a new entry never depended on the history fetch succeeding, so the add forms stay fully usable during someone else's outage.
- **One section throwing crashed the entire dashboard.** Confirmed with a temporary Suspense boundary made to throw deliberately (removed afterward): with no per-section error boundary anywhere in the tree, an unhandled exception in a single card's Server Component propagated all the way up and replaced the *whole page* with Next's generic "This page couldn't load," wiping out every other already-rendered card along with it — a single bug in, say, the Workout chart would have taken down Habits, Contacts, everything. Every card's Suspense boundary in `page.tsx` and `Header.tsx` is now wrapped in a new `SectionErrorBoundary` (necessarily a class component — `getDerivedStateFromError`/`componentDidCatch` have no hook equivalent) that renders neither a Suspense fallback nor `SectionLoadError`'s router-refresh Retry, but its own compact "Something went wrong loading X" plus a Reload page button — a caught render exception leaves that component's own React state broken in a way a background refetch can't clear, so a full reload is the one action that's honestly guaranteed to recover it. A new root `src/app/error.tsx` backs all of this up as a last-resort net for anything outside every individual boundary (e.g. `page.tsx` or `Header`'s own top-level code). Re-ran the same forced-throw test afterward: the broken section showed its own contained error while its siblings kept rendering normally.
- **Whoop's "As of [date]" timestamp couldn't tell you it was stale.** `getHealthSnapshot` already treats a *complete* fetch failure as "couldn't load" (shown via `SectionLoadError`, now with Retry), but a *partial* one — say, today's recovery hasn't synced but a 2-day-old cycle record still comes back — silently displays as a normal, neutral-gray timestamp indistinguishable from a fresh one. `HealthCardBody` now flags any snapshot older than 36 hours (Whoop typically syncs at least once a day) with the same amber/font-medium "needs attention" treatment established for due/overdue items dashboard-wide, and swaps the copy to "Data may be out of date — last synced [date]."

Two things were deliberately left as they already were, not overlooked: `getWeightGoal`, `getTodoistProjects`/`getUpcomingEvents`/`getHealthSnapshot` already draw this exact same null-vs-empty distinction from earlier work, so nothing needed to change there. And the Today at a Glance summary panel still quietly treats a null source as "nothing to show" (via `?? []` in `daily-glance.ts`) rather than surfacing its own error UI — consistent with how it already handled a null `workTasks`/`events`, on the reasoning that the full error state belongs on the actual card the user interacts with, not a convenience overview widget.

Verified with a Playwright preview mounting several of the updated components directly with `null` data (cleaned up afterward): `SectionLoadError`'s Retry button clicks without throwing; Grocery's items list shows the load error while its independently-loaded staples chips and "Add an item" form stay fully working; Journal's compose form and file upload stay usable while its entry history shows the load error; the Health card's "As of" line renders in neutral gray for a fresh snapshot and switches to amber "Data may be out of date" copy for a 50-hour-old one.

`src/app/loading.tsx` — the very first thing shown when the app opens, before `page.tsx` is ready to stream anything — used to mirror the entire dashboard grid as a wall of gray skeleton boxes. Replaced with a minimal, centered splash: a small uppercase "Life Dashboard" wordmark, a short motivational phrase below it, and three quietly breathing dots underneath, on the app's existing `bg-zinc-50 dark:bg-black` palette.

### Minimum Splash Duration

The splash now stays up for at least 2 seconds even when the dashboard's own initial data (the section order lookup in `page.tsx`, which is normally all that gates the route-level splash) resolves almost instantly — a deliberate, consistent entrance rather than a flash that's gone before the phrase is even legible on a fast connection. A slow load is never cut short or held any longer than it already naturally takes.

- **`ensureMinimumDuration(start, minMs = 2000)`** in the new `src/lib/splash.ts` is a floor, never a ceiling: it records elapsed time since `start` and waits out whatever's left of 2 seconds, or resolves immediately if the real work already took longer. `page.tsx` marks `start` at the top of its function body and awaits this right after its own data fetching, before returning any JSX — since Next's `loading.tsx` shows for exactly as long as `page.tsx` takes to resolve, this is the one place that actually controls how long the splash stays up.
- **`now()` wraps `Date.now()`** for the same reason `loading.tsx`'s phrase picker wraps `Math.random()` in its own named helper: the React Compiler's render-purity lint rule flags impure calls made directly in a component body, even though this route is never memoized and Next re-runs it fresh on every request regardless.
- **Deliberately scoped to the route-level splash only** — this doesn't touch how long any individual card's own Suspense skeleton shows once the splash itself is gone; those already take exactly as long as their own data needs, which was never the complaint.

Verified two ways. First, standalone: calling `ensureMinimumDuration` after ~50ms of simulated work totaled ~2000ms, while calling it after ~2600ms of simulated work totaled ~2600ms — not ~4600ms — confirming the floor never becomes an added delay on top of already-slow work. Second, end-to-end against real Next SSR timing (a temporary preview route wrapping the exact same fast/slow pattern in `Suspense` with the real splash as its fallback, cleaned up afterward): a near-instant fetch took ~2.0s total to resolve, and a ~2.6s fetch took ~2.6s total, matching the standalone results exactly.

### Splash Screen: Guaranteed on Every App Open

The previous splash relied entirely on `loading.tsx` — Next's Suspense fallback for `page.tsx`'s own async work — which turned out to only reliably show after signing in (a client-side transition, which React swaps via a plain in-page Suspense fallback) and not on a genuine fresh load: a hard reload, a brand-new browser tab, or relaunching the installed PWA from a home screen icon. Those are all real, separate HTTP requests where the browser streams (and may buffer or paint) the server response differently than an in-page client transition, so the exact same server-rendered fallback markup that reliably appears for one case went visually unnoticed for the other — `page.tsx`'s own `ensureMinimumDuration` floor was still running server-side in both cases, but a floor on when the server *sends* content doesn't guarantee anything about when or whether the browser *paints* the fallback that was sent.

Fixed by no longer depending on Suspense/streaming timing at all for the guarantee:

- **A new `AppSplashOverlay`** (a Client Component) is mounted once in the root `layout.tsx`, wrapping every route (`/`, `/login`, `/privacy` alike) rather than living inside `page.tsx`'s own Suspense boundary. Because it's part of every route's initial render, it's present in the very first HTML the browser gets for any real page load — no dependency on how that load's streaming happened to behave.
- **Its dismissal timer is anchored to `performance.now()`**, not to when the component happened to mount — that's time since the *browser's own navigation started*, so the same 2-second floor holds even if hydration itself took a moment, without ever double-counting time already spent.
- **It intentionally has no "already shown" memory** (no `sessionStorage`/cookie flag). A genuine fresh page load always remounts the root layout, so it always shows; an in-app client-side transition (signing out, or any future internal navigation) does *not* remount the root layout, so it correctly never re-shows — that's not a new app open, just moving around inside the one that's already running. This is also why the fix couldn't just be "make loading.tsx try harder": loading.tsx's boundary is scoped under the layout and gets swapped in and out per-navigation by design, while the whole point here was a signal tied to the actual page load, which only the persistent root layout has access to.
- **The markup itself was extracted into a shared `SplashScreen` presentational component** used by both `AppSplashOverlay` and the (now much simpler) `loading.tsx`, so there's one visual definition instead of two copies to keep in sync. `loading.tsx` stays in place as a backstop for whenever its own boundary specifically is what's pending (e.g. JS disabled, or a slow-hydrating client) — in normal operation the overlay is what's actually guaranteeing the outcome.
- **The phrase is still picked server-side** (`pickPhrase()` in `layout.tsx`, passed down as a prop) rather than inside the client component itself, specifically to avoid a hydration-mismatch: computing it independently during SSR and during client hydration would pick two different random phrases and trip React's text-mismatch warning.

Verified with Playwright against a fresh page load: the overlay is visible immediately, shows a phrase, and is removed from the DOM only after the 2-second floor plus its own exit fade have elapsed — with zero console/page errors (confirming no hydration mismatch). Separately confirmed, via a temporary two-page preview with a client-side `Link` between them, that the overlay does not reappear after an in-app client-side navigation, only on the initial load.

### Fixing the Blank White Screen on iOS Home Screen Launch

Even with the above, launching the installed PWA from an iPhone home screen icon (standalone mode) still showed a plain white screen instead of the splash — this was reported separately after confirming hard-refresh and new-tab both worked correctly. The root cause turned out to be a different layer entirely, not a bug in `AppSplashOverlay` itself:

- **iOS shows its own native launch-screen image for standalone-mode launches, before the WKWebView has loaded a single byte of this app's actual HTML/CSS/JS.** That native image is controlled exclusively by the (non-standard, Apple-specific) `<link rel="apple-touch-startup-image">` mechanism — the Web App Manifest's `background_color`/`theme_color`, despite an earlier comment in this codebase assuming otherwise, is not what iOS actually uses for this. With no `apple-touch-startup-image` links present at all, iOS had nothing to show but a plain white screen for that entire gap, regardless of anything `AppSplashOverlay` does — that component hadn't even had a chance to mount yet, since the page itself hadn't started loading.
- **A new dynamic `/apple-splash/[size]` route** (same `ImageResponse`-from-`next/og` pattern already used for `icon.tsx`/`apple-icon.tsx`) renders the exact same solid `#18181b` background plus centered `AppIconMark` used everywhere else in the app, at whatever exact physical pixel size a given device needs. It only ever serves one of a fixed, known set of sizes — enumerated once at module scope from the new `apple-splash-devices.ts` — rejecting anything else with a 404, since `ImageResponse` has no natural cap of its own and this shouldn't become an arbitrary-size image generator.
- **`apple-splash-devices.ts` lists 11 CSS-viewport/DPR buckets** covering the current iPhone lineup (SE/6 through 16 Pro Max) in portrait — Apple keeps the exact CSS width/height/device-pixel-ratio triple stable across several model generations even as the marketing name or physical resolution changes, so most entries cover more than one real device. `layout.tsx`'s `appleWebApp.startupImage` turns each into a `<link>` with the matching `media` query, most-specific devices listed first, plus one final entry with no `media` attribute at all as a catch-all for anything unlisted — order matters here, since a `media`-less link always matches and would shadow every more specific one after it if placed first. Landscape orientation isn't covered — a dashboard is realistically checked portrait, and doubling the list wasn't worth it for that case.
- **Middleware's PWA-asset allowlist needed a new entry.** iOS fetches `apple-touch-startup-image` the same cookie-less way it fetches the manifest and icons; without adding `/apple-splash/` to the same allowlist that already exempts `/manifest.webmanifest` and the icon routes, every one of these requests would have been redirected to `/login` (returning an HTML page instead of an image) for anyone not already signed in — silently breaking the exact thing this fix exists for.

The "timing issue where the white screen paints before the splash component mounts" half of the original hypothesis turned out not to be a separate bug: once iOS has a proper native image to show, the gap it's covering ends exactly when the WKWebView paints this app's first real frame — which, thanks to `AppSplashOverlay` living in the root layout and being fully server-rendered, already includes the splash's own styled background and content with no additional client-JS-dependent delay of its own.

Verified by fetching each of the 11 specific sizes plus the fallback directly and confirming a `200` with the exact requested pixel dimensions, confirming a request for an unlisted size correctly 404s instead of generating an arbitrary image, and confirming every `<link rel="apple-touch-startup-image">` tag in the rendered `<head>` carries the right `media` query for its size — including the unconditional fallback correctly appearing last with no `media` attribute at all.

### Personal Tasks: Today/Tomorrow/Upcoming Tabs

Personal Tasks now has the same three-tab layout Work Tasks already used — but where Work Tasks' due dates come from Todoist, Personal Tasks has no external source to pull them from, so this had to add the concept of a due date to Personal Tasks in the first place, not just the tabs on top of one that already existed.

- **A new nullable `due_date` column** (migration below) — nullable because a task with no due date is a normal, expected state here (an anytime task), not an error or something implying urgency the way it would for Work Tasks.
- **The add-task form gained an optional date input** next to the existing text field, and every task — dated or not — can have its due date set, changed, or cleared afterward via a small inline control: a due date shows as a clickable badge (click to change it), and an undated task shows a quiet "+ Add date" link in its place. This is the part of the request that doesn't have a Work Tasks equivalent to copy — since nothing external keeps this in sync, the UI itself has to be the only way to manage it. Saving is optimistic (the task re-buckets into the right tab immediately) and reverts with an error message if the save actually fails, matching this app's established pattern everywhere else.
- **Bucketing logic mirrors `TasksCardBody` exactly** — Today includes anything due today or overdue (with the same amber/font-medium treatment for overdue specifically), Tomorrow is due-tomorrow only, Upcoming is everything else including undated tasks. Since a personal task's due date is always a plain `"yyyy-mm-dd"` string (no time-of-day component the way a Todoist task's optionally has), the actual comparisons are simpler — direct string comparison instead of `Date` parsing — but the bucketing rules themselves are identical.
- **Today at a Glance's personal-tasks section changed too.** It previously listed every outstanding personal task unconditionally, because there was no due date to filter by yet — the comment explaining that was accurate when written and is now stale by construction. It now filters to due-today-or-overdue only, exactly like it already did for Work Tasks, so an undated or far-future personal task no longer shows up as if it needs attention today.

```sql
-- Personal Tasks has no external source (unlike Work Tasks/Todoist) to pull
-- due dates from, so this is a plain nullable column the user sets/edits
-- themselves — a task with no due date is treated as "no date yet", not
-- "due immediately" or an error.
alter table public.personal_tasks
  add column due_date date;
```

Verified with a Playwright preview (synthetic tasks: overdue, due today, due tomorrow, due next week, and one with no date): each landed in the correct tab; setting a due date on the previously-undated task via the inline "+ Add date" control immediately moved it into the Today tab, with no page reload, confirming the optimistic re-bucketing works as intended.

## Deploying to Vercel

1. Push this repository to GitHub (or your Git provider of choice).
2. Import the project into [Vercel](https://vercel.com/new).
3. Add `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `TODOIST_API_TOKEN`, `WHOOP_CLIENT_ID`, `WHOOP_CLIENT_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT` as Environment Variables in the Vercel project settings.
4. Deploy. Vercel will detect the Next.js framework automatically, including the weekly backup Cron Job defined in `vercel.json`.
5. In Google Cloud Console, make sure `https://<your-vercel-domain>/api/auth/callback/google` is registered as an authorized redirect URI for the OAuth client.
6. In the Whoop Developer Dashboard, make sure `https://<your-vercel-domain>/api/auth/callback/whoop` is registered as a redirect URI for the OAuth client.
